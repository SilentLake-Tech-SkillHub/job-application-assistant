# 岗位追踪表：唯一的状态记录

岗位追踪表（Excel）是投递流程**唯一的状态记录**。公司交接 JSON 只从 Excel 同版本导出，不独立写状态：公司扫没扫过、结论是什么、岗位投没投，都写在表里；过程证据（确认原话、截图、读回、审核包、回执）放在 [`投递证据/`](daily-batch.md)。

## 表结构与标签：以 campus-job-skills 为准

表结构、列序和标签值由 [campus-job-skills](https://github.com/SilentLake-Tech-SkillHub/campus-job-skills) 的 `【校招岗位收集与投递】campus-job-application/references/workbook-schema.md` 定义，盘点与汇报规则见同目录的 `research-progress.md`。本 Skill 不另写一套；本次共同授权的公司核对、计划明细、岗位目录、投递规则、内推信息五张共享明细表按公司交接契约维护，其他列、工作表或状态值不擅自新增；表结构变更须经用户批准，并在两个 Skill 里一起改。

投递流程用到的三处标签：

| 位置 | 取值 | 含义 |
|---|---|---|
| `校招计划` 表 `盘点状态` | `已有相关岗位记录` / `无当年校招计划` / `无用户要求岗位` / `无法访问校招页面` / `尚未推进` | 公司（按计划行）的招聘结论，五个值之一，不附加文字 |
| 地区岗位表 `投递状态` | 空白（公司占位行）/ `待投递` / `已提交` | 岗位行的投递结果 |
| 地区岗位表 `备注` | 文字 | 例外与原因：本批留空、受阻、停止决定、资格说明等，写日期和批次 |

## 什么时候写什么

| 事件 | 写入 |
|---|---|
| 打开一家公司的校招页面、看过计划或岗位（**只要扫过**） | 当场把该公司 `盘点状态` 从 `尚未推进` 改成另外四个值之一；`尚未推进` 只留给真正没碰过的公司 |
| 找到范围内岗位 | 每岗一行（先填公司占位行，再在该公司行下方插入），`投递状态` 写 `待投递`；公司 `盘点状态` 写 `已有相关岗位记录` |
| 校招页面打不开 / 今年没开校招 / 没有用户要求的岗位 | `盘点状态` 写 `无法访问校招页面` / `无当年校招计划` / `无用户要求岗位`，`备注` 写日期、批次和证据位置 |
| 本批留空（补位规则选「留空」）或受阻 | 标签按上一行写；`备注` 写“<日期> <批次>：留空/受阻，原因…，证据 投递证据/…” |
| 拿到官方回执 | 岗位行 `投递状态` 改 `已提交`，并在同一轮重开工作簿读回 |
| 结果不确定、点击后无回执 | 保持 `待投递`，`备注` 写“结果待核”，先查申请中心 |

`投递状态` 只表达投递结果。`待投递` 是记录了但没投，不代表用户已选岗或授权填表；填写进度、`prepared`、审核版本这类过程状态只体现在 `投递证据/` 的文件和 `填写方案.json` 里，不写进表格。

## 填写缓存与 Excel 的分工

表单填写有一份每岗的 JSON 缓存 `填写方案.json`（[批量填写与填写缓存](browser-application.md#批量填写与填写缓存三条通道通用)）。它和 Excel 的分工固定如下，**两边互不代写**：

| | Excel 追踪表 | `填写方案.json`（岗位目录） | Markdown 证据（岗位目录） |
|---|---|---|---|
| 记什么 | 公司 `盘点状态`、岗位行 `投递状态`、`备注` | 这一张表单每个字段的定位、填法、值或值来源、逐字段 `状态`（待填/已填/已读回/不一致/需用户/跳过）与读回 | 确认原话、填写读回、草稿读回、审核包、批准、目标确认、提交前复核、提交已点击、回执、结果不确定、追踪表读回 |
| 是谁的依据 | **唯一的状态记录**：投没投、扫没扫、结论是什么 | 只是填写进度的缓存，删掉也不改变任何状态 | 门禁检查的过程证据 |
| 不能写 | 填写进度、审核版本等过程状态 | 盘点状态、投递状态、批准、回执等任何状态字段（填写工具按键名白名单拒绝） | — |

**什么事件写哪里：**

| 事件 | Excel | `填写方案.json` | 证据文件 |
|---|---|---|---|
| 扫过公司 / 找到岗位 | 写 `盘点状态`；每岗一行 `待投递` | 不存在 | 岗位包、资格核对 |
| 开始填表（`--stage prepare` 通过后） | 不变 | 由控件盘点或站点模板生成；**生成前 Excel 必须已有这一行**（没有行的岗位目录会被门禁拒绝） | 控件盘点 |
| 批量 / 点击 / 上传填写 | 不变 | 每个字段填完即读回并写 `状态` | — |
| 填写中断 | 不变 | 保留进度；续跑先复核已读回字段 | — |
| 全部读回 | 不变 | 导出 | `填写读回.md`（带方案哈希） |
| 保存草稿并重开 | 不变 | 不变 | `草稿读回.*` 或 `无草稿说明.md` |
| 审核、批准、目标确认 | 不变 | 不变（实际表单/材料内容变化才更新读回与审核版本；仅缓存变化不影响批准） | 审核包、批准、目标确认 |
| 点击提交 | 不变（仍 `待投递`） | 不写 | 钩子写 `提交已点击.md` |
| 点击后查申请中心确认没提交上 | 不变（仍 `待投递`） | 不写 | `提交核查.md`（结论: 未提交），之后可重新提交 |
| 拿到回执 | **当场**改 `已提交`，重开读回 | 不写 | 回执、追踪表读回 |
| 结果不确定 | 保持 `待投递`，`备注` 写“结果待核” | 不写 | `结果不确定.md` |

**缓存校验与独立门禁：**

- 填写工具负责缓存的字段白名单、值来源、控件和目标身份检查；执行时可用 `--workbook` 只读核对 Excel 唯一待投递行。缓存可删，丢失后重新盘点生成；它不保存盘点/投递状态。
- **门禁不读取、不要求、不解析 `填写方案.json`**。删掉 JSON、修改它或缓存损坏，不会改变任何门禁结论、Excel 状态和完成计数，也不作废独立审核批准。
- 审核和提交仍要求独立 `填写读回.md`、草稿重开读回或无草稿说明、审核包、批准及目标确认；导出中的方案哈希只记录来源，不与缓存实时比较。实际表单或材料变化仍须更新独立读回和审核包，旧审核批准随版本变化失效。
- 回执 ⇔ `已提交`、追踪表读回与提交点击标记都独立检查；删除缓存不能清除未核实的提交尝试或解除防重投保护。
- `batch_check.py` 的 `填写进度` 仅为可选展示，不计入目标或完成数；`stage_gate.py --stage closeout` 与 `batch_check.py --closeout` 都关闭缓存展示读取。

## 写入规程

- 写入前重新读取工作簿，记录 SHA-256，复制一份可恢复的备份。
- 只改受影响的单元格，保留其他工作表、公式、数据验证和用户编辑；不依赖记住的行号，按 `岗位链接`（岗位行）或 `公司`（计划行）重新定位。
- 保存后立刻用 `scripts/tracker_readback.py` 对照备份读回：目标行取值正确，其他行、占位行、其他工作表和公式不变，没有 `#REF!` 之类错误值。读回结果用 `--record` 存成岗位目录里的 `追踪表读回.md`。
- 文件在编辑期间被别的进程改过时，先合并最新内容，不能覆盖。

## 身份与去重

- 公司官方招聘入口、当前计划和岗位**直链**是三个层次，分别核实；列表页或猜测的链接不算岗位直链。
- 以直链（规范化后去掉 utm_*、ref、source 等跟踪参数）为主键去重；链接变化时再比对公司、岗位名、BU、地点和官方岗位 ID。同名不同 BU / 城市 / ID 不合并，多城市同一 ID 不重复成多行。BU 缺失写 `未披露`。
- 打开新申请前同时查站点申请历史和表格状态。

## 状态冲突

站点证据与表格不一致时，以[阶段契约第 7 节](stage-contract.md#7-状态冲突时以谁为准)的优先级为准：站点申请中心 > 官方回执 > `投递证据/` 记录 > 表格。逐条列出受影响的岗位，不批量改状态、不重投；有官方回执的提交当场入账为 `已提交`。

## 自动检查

`scripts/batch_check.py` 和每个阶段门禁都会核对：

- 本批扫过的公司（有 `投递证据/<批次>/公司/<公司>/` 或岗位目录）`盘点状态` 不能是 `尚未推进` 或空白；
- `盘点状态` 只能是五个固定值；`已有相关岗位记录` 的公司必须有带直链的岗位行；
- 岗位目录里有回执 ⇔ 表格 `投递状态` 为 `已提交`，且有 `追踪表读回.md`；
- `投递状态` 只能是 `待投递` / `已提交`，公司占位行留空；直链不重复。
- JSON 缓存的合法性由填写工具检查，不进入阶段门禁；
- 有 `提交已点击.md` 的岗位必须有回执或 `结果不确定.md`。

这些检查只看结构，不能证明网站真的保存或收到了申请。

偏好、城市排序和逐岗证据的规则见[偏好证据契约](preference-contract.md)；默认岗位次序与公司动作前确认见[同一契约](preference-contract.md#默认次序与公司动作前确认)。

## 公司方案导出与刷新

[公司核对交接](company-review-handoff.md)规定的 `岗位交接/<批次>/公司方案.json` 与 `填写方案.json` 用途不同：前者从 Excel 导出计划/目录/规则/内推/最终选择及现有表记录，供交接校验；后者只是表单填写缓存。`tracker_readback.py` 成功后自动重导已建立的所有批次公司方案；其他Excel编辑路径确认读回后也必须重新导出前者，每次规则刷新、选岗改变、回执入账或其他工作簿变化后都同步。JSON缺失或陈旧不改变Excel事实，但阻断下一Prepare/Review/Submit。禁止从旧JSON回写覆盖主表或伪造确认。

整本业务 JSON 与独立志愿也是固定交接输入；原表和共享表更新统一走[数据建设与固定脚本](storage-workflow.md)，每次刷新全部现有批次。提交目标的意向必须与同版志愿明细逐项一致。
