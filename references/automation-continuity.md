# 自动化连续推进：多通道切换与交接点

目标是在用户已确认的范围内连续推进，保留必要的授权和本人操作步骤。浏览器默认内置浏览器与 Chrome（Chrome 插件）双通道并行，按公司分配；没有 Chrome 插件时先问用户能否用 Playwright 代替，规则见[浏览器分工](browser-application.md#浏览器分工内置浏览器与-chrome-默认并行)。每个通道内可使用已授权且受支持的控件接口；权限拒绝、安全限制或本人操作要求不能换通道规避。短信结果和图形验证默认由用户提供/完成，完整接手及微信截图交接按对应子Skill的三次确认流程执行。

## 1. 批次开始时的能力预检（Query 阶段完成，不留到流程中途）

在 Query 阶段按当前实际暴露的工具检查可用能力；工具说明中的禁止项优先，不为凑齐通道而安装依赖、获取权限或启动外部脚本。只报告与本次任务有关的缺失能力和真实本人操作点，不重复同批有效授权：

| 检查项 | 怎么查 | 缺失时 |
|---|---|---|
| 内置浏览器通道 | 能否列出/控制内置浏览器标签页 | 告诉用户；全部公司改走 Chrome 通道 |
| Chrome 通道（Chrome 插件，如 Claude in Chrome） | 插件工具是否出现在本会话、能否列出用户 Chrome 标签页 | 询问用户能否用 Playwright 代替；明确同意才启用并记录，否则只用内置浏览器 |
| 桌面操作（computer use） | 当前会话是否有屏幕截图与点击桌面应用的工具。Claude Code 需在 `/mcp` 中启用 `computer-use`；macOS 首次使用时授予「辅助功能」「屏幕录制」，Windows 以工具实际返回的可用状态为准 | 说明启用方法；在启用前用下一通道兜底 |
| 系统脚本（仅 macOS `osascript` / System Events） | 能否读取前台应用窗口 | macOS：需在「隐私与安全性→辅助功能」允许终端，由用户本人开启。Windows/Linux：记为不适用，不另装或改用其他脚本代替 |
| Playwright（仅作 Chrome 通道的替代） | 依赖是否安装、能否连接用户指定的浏览器会话 | 只在用户同意替代时检查；不可用时如实说明，保留内置浏览器通道 |
| 执行 Agent 自身不能执行的步骤 | 按执行 Agent 所在平台规则逐项列出（例如某些 Agent 不处理人机验证、不输入短信验证码或证件号） | **在 Query 时一次性说明**，给出符合平台规则的用户操作或集中交接安排；不得换执行方绕过限制 |

预检结果写入私有批次记录 `channels`。权限开启属于系统安全设置，只能由用户本人操作；Agent 给出准确路径。

## 2. 浏览器双通道

内置浏览器与 Chrome 通道同时推进不同公司，同一家公司只在一个通道里操作。通道分配、缺少 Chrome 插件时询问 Playwright 代替、运行中断开的处理，以及 computer use / 系统脚本的确认要求，统一见[浏览器分工](browser-application.md#浏览器分工内置浏览器与-chrome-默认并行)，此处不另设规则。

换通道或启用替代工具不扩大数据、公司、岗位、登录、最终投递或验证码接手授权，不绕过站点安全拒绝及本人操作要求。最终目标/表单版本仍按父Skill审批。

## 3. 推进到交接点前的最后一步

交接点与确认点的完整清单（H1–H15，含次序确认、版本批准、名额不足选岗、资格待核、跨轴冲突、新协议、Playwright 代替等）只在[阶段契约第 5 节](stage-contract.md#5-交接点与确认点完整清单)维护；本节说明如何推进到交接点。

到达交接点之前，把能做的全部做完。例如：
- 手机验证码登录：填号码 → 按已确认条款模式处理 → 点「获取验证码」→ 普通验证点击由 Agent 做，图形默认交用户 → 等待用户提供/输入短信码；完整接手另走三次确认及平台允许的分支。
- 微信登录：打开不含授权效果的微信入口 → 完成三次截图交接确认 → 平台允许时发最少截图到已核验的用户私密渠道 → 用户扫码/本人授权 → 等待回跳并核对账号。Agent 不点快捷确认或 OAuth「允许」。
- 填表：交接前把其余所有字段填好、保存草稿，交接只剩那一个字段。

## 4. 交接格式与集中处理

每次交接必须包含：
1. 已经完成的步骤；
2. 平台允许的当前页面截图（遮盖证件号、验证码等秘密；微信二维码另按三次确认后的私密交接范围处理）；
3. 用户要做的**唯一**动作及位置；
4. 用户完成后 Agent 接着做什么。

不要在一个公司卡住时空等：标记该公司的交接项，继续推进其他独立公司；最后把所有交接项合并成一条消息，让用户一次处理完。提交前目标确认同理，按公司汇总成一张清单一次确认；但该公司数量规则为 `未核实` 时，只确认第一个目标，提交后读回账号状态再确认下一个（父Skill数量规则门禁）。

## 5. 批量登录与逐家推进（Issue #11）

逐家“打开→登录→填写→投递”会让用户在每家登录时都等待，吞吐太低。改为批量：

1. **Query 定范围后分组开站**：复用当前公司页面，按[浏览器分工](browser-application.md#浏览器分工内置浏览器与-chrome-默认并行)把公司分到内置浏览器或 Chrome 通道并行开站；Chrome 通道按[浏览器标签分组](chrome-window-grouping.md)每窗口10页、第11页新建窗口。不同公司可同窗，但每个标签保留公司身份；列表、岗位、登录、表单均计入网页数。10仅控制窗口分组，不是公司总量，也不授权补位或扩组；不能为了凑数或吞吐打开范围外公司。
2. **公司动作前确认后做到安全交接点**：先按同一岗位清单汇报公司、BU、办公地和岗位,确认相对本批默认次序有无变化；没有同批公司确认时只读开站,不进行申请动作。已确认的公司再复用现有登录态，按用户选择打开登录入口、填号码、勾选已充分授权的条款、点获取验证码；微信确认由用户操作，不为减少交接自动授予权限。
3. **一条消息集中交接登录**：列出所有待登录站点、每个站点用户要做的唯一动作和截图位置；用户集中处理。已经处于登录态的站点不打扰用户。
4. **用户登录期间不空等**：先推进已登录或无需登录的公司（核对账号历史、读取投递规则、上传附件、填写在线简历并保存草稿）。
5. **按公司汇总决策后集中询问**：志愿/部门/城市/调剂等用户选择项，以及简历缺失的个人信息，按公司整理成一次提问；拿到答复后一次填完。
6. **逐家提交**：每家按父Skill的提交前目标确认门禁，汇总成一张清单一次确认；确认后提交、读回、存档、记账，保留本公司回执及整组未完成页面，再进入下一家。没有另行明确的公司/页面关闭指令，不清理批次标签。

保护规则：
- 正在填写的表单页只用显式 tabId 操作；查资料另开标签页并显式传入新 tabId，避免把表单页导航走。
- 草稿保存时机按[浏览器准备](browser-application.md#page-init-reload-and-injection-discipline)的单一规则：有草稿的站点每栏保存，必填完成后再保存并重开读回；无草稿站点先问完所有决定再一次填完。
- 每个标签页记录公司、阶段（待登录/已登录/填写中/待确认/已投递）与下一步，用户可随时看到整批进度。
- 回合结束、验证码交接及单岗提交后均按浏览器引用保留可见标签并读回；内部handoff标记不能单独证明用户可见页面仍在。

## 6. 记录

在私有批次记录写入：`channels`（预检结果）、`browser`（每家公司的 `browser_lane`，以及 `playwright_substitute` 的同意依据）、每次通道切换、交接项（公司、步骤、原因、截图位置、完成时间）。不记录验证码、证件号、Cookie。

## 独立偏好与执行证据

批量分阶段开站/登录/填表保留；在每岗表单前先交付 [逐岗证据包](preference-contract.md)，交接和 closeout 必须报告实际 fill/save/submit 状态与来源，不能停在只报登录。默认岗位次序与公司动作前确认的唯一规则见[偏好契约](preference-contract.md#默认次序与公司动作前确认)。
