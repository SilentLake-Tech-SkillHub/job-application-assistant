# 自动化连续推进：多通道切换与交接点

目标是在用户已确认的范围内连续推进，保留必要的授权和本人操作步骤。工具不可达时可尝试其他受支持通道；权限拒绝、安全限制或本人操作要求不能换通道规避。短信结果和图形验证默认由用户提供/完成，完整接手及微信截图交接按对应子Skill的三次确认流程执行。

## 1. 批次开始时的能力预检（Query 阶段完成，不留到流程中途）

在 Query 阶段按当前实际暴露的工具检查可用能力；工具说明中的禁止项优先，不为凑齐通道而安装依赖、获取权限或启动外部脚本。只报告与本次任务有关的缺失能力和真实本人操作点，不重复同批有效授权：

| 检查项 | 怎么查 | 缺失时 |
|---|---|---|
| 浏览器网页操作（如 Chrome 扩展） | 能否列出/控制标签页 | 请用户连接浏览器扩展 |
| 桌面操作（computer use） | 当前会话是否有屏幕截图与点击桌面应用的工具。Claude Code 需在 `/mcp` 中启用 `computer-use`，并在首次使用时授予 macOS「辅助功能」「屏幕录制」 | 说明启用方法；在启用前用下一通道兜底 |
| 系统脚本（macOS `osascript` / System Events） | 能否读取前台应用窗口 | 需在「隐私与安全性→辅助功能」允许终端；由用户本人开启 |
| Playwright | 依赖是否安装、能否连接用户指定的已登录浏览器会话 | 记录不可用，不影响其他通道 |
| 执行 Agent 自身不能执行的步骤 | 按执行 Agent 所在平台规则逐项列出（例如某些 Agent 不处理人机验证、不输入短信验证码或证件号） | **在 Query 时一次性说明**，给出符合平台规则的用户操作或集中交接安排；不得换执行方绕过限制 |

预检结果写入私有批次记录 `channels`。权限开启属于系统安全设置，只能由用户本人操作；Agent 给出准确路径。

## 2. 通道顺序与切换

按当前执行平台支持范围选择工具，不把下面列表当作必须全部调用的固定顺序。优先专用接口及目标浏览器内的语义控件；只有实际失败或控件在浏览器外才考虑其他获准通道：

1. **专用连接器/接口**（如邮箱连接器）。
2. **浏览器网页工具**：网页内的登录、填表、上传、勾选。
3. **computer use**：已授权的系统文件选择框、原生对话框及网页工具无法触达的普通控件；微信授权「允许」由用户本人操作。
4. **系统脚本**（osascript/System Events）：computer use 不可用时操作已授权的普通桌面控件，不代点微信授权或其他本人操作按钮。
5. **Playwright**：需要精确定位、逐字输入或稳定重试的网页控件（见[字段绑定恢复策略](field-binding-recovery.md)）。

切换只改变操作手段，不扩大授权：哪些子Skill能用仍以[自动化授权](automation-authorization.md)为准，最终投递仍受父Skill的提交前目标确认门禁约束。每次切换记录原因和结果。

## 3. 推进到交接点前的最后一步

交接点只有以下几类：

- 提交前目标确认（Issue #8 硬门禁）。
- 未授权的自动化子Skill对应步骤，或执行 Agent 在预检中已声明不执行的步骤。
- 必须由本人完成的物理动作：手机扫码、手机端确认、生物识别、系统权限开启。
- 缺失且只能由用户提供的事实（如简历未写的信息）。

到达交接点之前，把能做的全部做完。例如：
- 手机验证码登录：填号码 → 按已确认条款模式处理 → 点「获取验证码」→ 普通验证点击由 Agent 做，图形默认交用户 → 等待用户提供/输入短信码；完整接手另走三次确认及平台允许的分支。
- 微信登录：打开不含授权效果的微信入口 → 完成三次截图交接确认 → 平台允许时发最少截图到已核验的用户私密渠道 → 用户扫码/本人授权 → 等待回跳并核对账号。Agent 不点快捷确认或 OAuth「允许」。
- 填表：交接前把其余所有字段填好、保存草稿，交接只剩那一个字段。

## 4. 交接格式与集中处理

每次交接必须包含：
1. 已经完成的步骤；
2. 平台允许的当前页面截图（遮盖证件号、验证码等秘密；微信二维码另按三次确认后的私密交接范围处理）；
3. 用户要做的**唯一**动作及位置；
4. 用户完成后 Agent 接着做什么。

不要在一个公司卡住时空等：标记该公司的交接项，继续推进其他独立公司；最后把所有交接项合并成一条消息，让用户一次处理完。提交前目标确认同理，按公司汇总成一张清单一次确认。

## 5. 批量登录与逐家推进（Issue #11）

逐家“打开→登录→填写→投递”会让用户在每家登录时都等待，吞吐太低。改为批量：

1. **Query 定范围后分组开站**：复用当前公司页面，遵守工作区要求的独立公司窗口及保护规则。岗位、列表、登录、表单可按实际需要保留多个标签页；不把单标签页或固定数量当作硬限制。按实际工具容量和浏览器负载分组，不能为了吞吐打开范围外公司。
2. **公司动作前确认后做到安全交接点**：先按同一岗位清单汇报公司、BU、办公地和岗位,确认相对本批默认次序有无变化；没有同批公司确认时只读开站,不进行申请动作。已确认的公司再复用现有登录态，按用户选择打开登录入口、填号码、勾选已充分授权的条款、点获取验证码；微信确认由用户操作，不为减少交接自动授予权限。
3. **一条消息集中交接登录**：列出所有待登录站点、每个站点用户要做的唯一动作和截图位置；用户集中处理。已经处于登录态的站点不打扰用户。
4. **用户登录期间不空等**：先推进已登录或无需登录的公司（核对账号历史、读取投递规则、上传附件、填写在线简历并保存草稿）。
5. **按公司汇总决策后集中询问**：志愿/部门/城市/调剂等用户选择项，以及简历缺失的个人信息，按公司整理成一次提问；拿到答复后一次填完。
6. **逐家提交**：每家按父Skill的提交前目标确认门禁，汇总成一张清单一次确认；确认后提交、读回、存档、记账、关闭该公司标签页，再进入下一家。

保护规则：
- 正在填写的表单页只用显式 tabId 操作；查资料另开标签页并显式传入新 tabId，避免把表单页导航走。
- 没有草稿保存的站点，先问完所有决定再一次填完，缩短未保存窗口；有保存按钮的站点每完成一个栏目就保存。
- 每个标签页记录公司、阶段（待登录/已登录/填写中/待确认/已投递）与下一步，用户可随时看到整批进度。

## 6. 记录

在私有批次记录写入：`channels`（预检结果）、每次通道切换、交接项（公司、步骤、原因、截图位置、完成时间）。不记录验证码、证件号、Cookie。

## 独立偏好与执行证据

批量分阶段开站/登录/填表保留；在每岗表单前先交付 [逐岗证据包](preference-contract.md)，只在硬范围内推进，跨轴冲突和明确选岗不代选。交接和 closeout 必须报告实际 fill/save/submit 状态与来源，不能停在只报登录。偏好变更保留提交与选岗，复用 JD，仅按指定缺口复查；既有验证码/微信/条款、账号独占与最终目标及表单版本门禁不变。

每批先向用户要默认岗位次序，保存同批确认，不沿用上一批。每家公司开始申请操作前，先用同一逐岗包展示公司/岗位/BU或未披露/办公地，确认相对默认次序有无变化；company_order_confirmation_ref 和 pre_form_report_ref 对应同一包。交接复用这份记录，最终具体目标和当前表单版本继续审核，不另建三套脱节清单。
