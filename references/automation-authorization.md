# 自动化授权：Query、模式与记录

五个自动化子Skill默认关闭。它们处理的是登录凭据、短信、人机验证、个人隐私和法律条款，任何一项被误用都会直接影响用户账号或留下错误承诺，因此每一项都要先由用户明确开启，才能在本批次调用。

| 子Skill | 处理内容 | 永久边界（任何模式都不变） |
|---|---|---|
| [login-phone-otp](../skills/login-phone-otp/SKILL.md) | 填手机号、请求短信；默认由用户提供或输入结果 | 完整接手需三次确认及明确短信来源权限；只用本次新码，绝不保存；遵守平台限制 |
| [login-wechat](../skills/login-wechat/SKILL.md) | 打开微信入口；三次确认后按平台允许范围发截图到已核验的用户私密渠道 | 用户扫码/操作；Agent 不点快捷确认或 OAuth“允许”，不扩大持续权限 |
| [captcha-solve](../skills/captcha-solve/SKILL.md) | 普通验证点击由 Agent 完成；图形挑战默认交用户 | 完整接手需三次确认及平台允许；同一挑战最多 2 次；不绕过风控或访问限制 |
| [privacy-info-fill](../skills/privacy-info-fill/SKILL.md) | 电话、邮箱、地址等个人信息填写 | 证件号码由用户本人填写；缺失信息向用户索取 |
| [terms-consent](../skills/terms-consent/SKILL.md) | 先选逐项查看或本次全部代勾；代勾需三次确认 | 已覆盖普通项不重复问；保留具体新协议披露/接受、持续权限逐次确认、本人操作及最终投递门禁 |

## Query

在批次 Query 阶段、任何登录或填写动作之前，问一次：

> 本轮是否开启自动化子Skill？可选：①不开启（对应步骤由你本人操作）②半自动：只开启其中几项（请列出）③全自动：5项全部开启，但仍保留上表中的用户步骤和确认要求。短信结果默认由你提供，图形验证默认由你完成；完整接手另需三次明确确认。条款方面，你想逐项查看后确认，还是由我在本次已确认的求职范围内全部代勾？选择全部代勾需三次明确确认。

- 没有回答、回答含糊（如“你看着办”“继续”）或只批准了别的事项（如批准投递某岗位）时，按“不开启”处理。批准投递不等于开启自动化子Skill。
- 用户明确选择“全自动”或“五项全部开启”时，直接记录五项已开启，并简要告知永久边界；不再追问是否开启。条款处理方式尚未选择时只问这一缺失项。此选择不替代完整接手验证、微信截图交接或全部代勾各自所需的三次明确确认。
- 用户可随时收回或追加某一项；以最新的明确指令为准，并更新记录。
- 授权只对当前已确认批次及范围有效。同批续跑或换执行Agent先读回授权依据、撤销和平台能力；有效授权继续使用，不因换Agent再问开启。新批次重新 Query；新增公司、数据、接收方、协议或权限时只处理实质变化及缺失项。不同Agent不能沿用另一执行平台的能力或豁免其限制。

## 三次明确确认（用户自定的额外流程）

需要三次确认的分支分别是：完整接手验证（注明短信/图形及范围）、微信私密截图交接、本次求职流程全部代勾。只对用户选择的分支进行；三次是本 Skill 的用户自定额外流程，不是平台标准。

1. **第一次：范围**。说明本次求职流程、公司范围、具体动作及目标；微信截图还需说明内容、用途和已核验的本人私密渠道，短信需明确可读取的来源。取得用户明确同意。
2. **第二次：后果**。说明该分支的具体风险（验证失败/风控、认证截图泄露，或同意条款和处理申请资料的后果），请用户确认理解并愿意自行承担所述风险。
3. **第三次：最终确认**。重申已确认的范围和仍需保留的平台批准、本人操作及最终投递边界，取得开始该分支的明确答复。

三次须有三个分别对应问题的明确答复；不将一次“全部同意”、三个预勾选项、沉默或对其他事项的同意算作三次。记录答复依据，不记录验证码等秘密。同一分支、同一本次范围内不重复这套流程；实质范围变化时仅处理新增授权要求。用户可撤销。

责任声明不构成对平台规则、安全限制或网站权限的豁免。具体新法律协议仍按平台要求先披露并取得接受，创建/扩大持续权限仍按平台要求逐次确认，必须本人完成的动作仍交用户；不得换工具绕过拒绝。全部代勾仅限本次求职，已覆盖普通项不逐项重复问，不添加主观“异常”门槛反复追问。

## 能力预检与连续推进

授权 Query 同时完成[连续推进](automation-continuity.md)的能力预检：可用通道（浏览器、computer use、系统脚本、Playwright）、缺失通道的开启方法，以及执行 Agent 按自身平台规则不执行的步骤及替代安排。这些在 Query 时一次说清，不留到流程中途。

## 模式

- **未开启**：子Skill不调用。Agent只完成不涉及上述内容的工作，到登录、验证码、个人信息、条款处停下，请用户本人操作后继续。
- **半自动**：只调用已批准的子Skill及分支；未批准的步骤交给用户。手机登录默认由 Agent 请求短信、用户提供码；条款按已选的逐项查看或三次确认后的本次代勾处理。
- **全自动**：5项全部开启，但上表右列的永久边界不变。

两种模式都不改变父Skill的最终投递门禁：每个岗位仍需用户按审核版本单独批准才可提交。

## 提交前目标确认门禁（硬门禁，任何模式不豁免）

除岗位级批准外，每次点击投递前还必须执行父Skill的**提交前目标确认门禁**（Issue #8）：向用户逐项展示并确认 **公司、BU/业务集团/招聘主体、办公地、岗位、意向部门/志愿槽位（多意向按投递顺序）**，用户对这一确切目标明确确认后方可点击。概括性指令（如「帮我填写打勾提交」「后面的你帮我提交」）只授权操作本身，不满足本门禁；意向部门、志愿顺序、调剂选项等**用户选择权槽位**，Agent 只能列选项给建议，不得代为选择。用户无法确认时停在提交前并记 `待确认`，不得点击。多个网站终止投递不可逆（终止后该业务集团本季不可再投），此门禁因此不可被半自动/全自动模式覆盖。

## 记录

在私有批次记录（不进入公开Skill、Issue或截图）写入：

```json
{
  "automation_mode": "off | semi | full",
  "approved_subskills": ["login-phone-otp", "terms-consent"],
  "approval_ref": "时间 + 用户原话摘要",
  "sms_read_allowed": false,
  "verification_mode": "user_result | agent_takeover",
  "terms_mode": "per_item | current_workflow_all",
  "confirmed_scope": "本次流程、公司范围、动作、必要的数据来源/私密交接渠道",
  "confirmation_refs": {
    "verification_takeover": [],
    "wechat_handoff": [],
    "terms_batch": []
  },
  "revocations": []
}
```

每个子Skill开始前读取这条记录；记录里没有自己的名称就不执行，直接把该步骤交还父Skill并说明需要用户本人完成或重新授权。
