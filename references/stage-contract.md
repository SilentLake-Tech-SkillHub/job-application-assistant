# 阶段契约：入口、问题时机、确认点、交接点与收尾

本文件是以下规则的**唯一出处**；其他文件只引用这里，不再复制条文。字段名对应私有批次 JSON（见 [daily-batch](daily-batch.md)），由 `scripts/validate_batch.py` 与 `scripts/stage_gate.py` 做结构校验。

## 1. 入口判定（谁来处理这个请求）

| 用户请求 | 判定 | 处理 |
|---|---|---|
| 只研究公司、收集岗位、整理岗位表，没有提出申请动作 | `research` | 转工作区的研究/收集流程（如 campus-job-skills），本 Skill 不启动 |
| 对**已确认的岗位清单**或指定的现有岗位，要求准备表单、存草稿、审核或投递 | `application` | 进入本 Skill |
| 同时要求"找岗位并投递" | 先 `research` 再 `application` | 发现与首轮 JD 核验由研究流程完成并交出岗位清单；本 Skill 从该清单开始，只对清单做投递前复核，不重复首轮扫站 |
| 措辞不明 | 先问一句"这次是只收集岗位，还是要进入申请准备？" | 未答复前不开表单 |

判定写入 `batch.entry = {intent, basis, ref}`：`basis` 记用户原话摘要或交接来源，`ref` 指向依据。`intent` 不是 `application` 时校验器拒收该批次。

## 2. 启动读取与缺失处理

从工作区路由读取：私有档案、当前批次记录、岗位追踪表、投递简历。每个文件记入 `batch.sources[]`：`{name, ref, sha256, read_at}`（`ref` 用工作区内的别名或相对路径，不写个人信息）。

| 缺什么 | 处理 |
|---|---|
| 路由 | 请用户指出文件位置；不在 Skill 目录或公共目录里新建 |
| 个人档案 | 复制 [空白模板](../skills/personal-info-vault/assets/profile-template.md) 到工作区私有目录，登记后使用 |
| 批次记录 | 新批次：按 Query 新建；续跑：说明找不到并请用户确认是新批次还是指出旧记录，不凭记忆续跑 |
| 追踪表 | 请用户提供；没有追踪表时只能准备、不能写"已提交" |
| 投递简历 | 必问；没有确认的简历不开任何表单 |

缺失项写 `{name, status: "missing", handling}`，不得写空 Hash 冒充已读。

## 3. Query：开始前必问 vs 到步骤前再问

**开始前必问**（一次问完；任一项未定时，不开站、不登录、不开表单，只做离线整理）：

1. 硬范围：地区、届别、用工、岗位职责、城市。
2. 三条偏好轴与实习政策（见 [偏好契约](preference-contract.md)）。
3. 本批默认岗位类别次序。
4. 分桶、计数口径（`checked`/`eligible`）、补位规则（`replace`/`keep_gap`，见第 9 节）、数字目标或停止条件。
5. 投递材料（简历文件与版本，记 `batch.materials[]` 的 Hash）与选岗/准备授权范围（第 4 节）。
6. 执行方式：一个 AI 还是多个 AI。
7. 自动化子 Skill 开启方式与条款处理方式（[自动化授权](automation-authorization.md)）。
8. 能力预检结果与执行 Agent 声明不做的步骤（[连续推进](automation-continuity.md)）。

**到步骤前再问**（届时按公司汇总成一条消息，不在 Query 预先追问）：

- 每家公司相对默认次序有无变化（开始该公司申请动作前）。
- 简历和档案都没有的个人事实（填表时按公司汇总）。
- 志愿/意向部门/调剂/城市等用户选择项（填表时按公司汇总，Agent 只给建议）。
- 名额不足时选哪几个岗位（查到数量规则后）。
- 资格待核或不符时是否仍以真实材料尝试（资格复核后）。
- 跨轴冲突的取舍。
- 具体新法律协议的接受、新增持续权限（遇到时）。
- computer use 首次使用、Playwright 代替 Chrome 通道（需要时）。
- 审核版本批准与提交前目标确认（Review / Submit）。

## 4. 授权覆盖范围与必停情形

Query 中用户确认"准备授权"后（`batch.preparation_authorized` 与 `batch.role_selection_authorized`，依据 `batch.authorization_ref`），Agent **无需逐岗先问**即可：在硬范围内选岗、登录（按已开启的子 Skill）、填写普通字段、上传已确认材料、保存草稿。

即使已授权，以下情形**必须停下等用户**，且不受"全自动"影响：第 5 节交接点表中标为"必停"的各项。"每家公司开始前确认次序"不要求逐家打断：可把多家公司的逐岗包合并成一条消息一次确认，未确认的公司只读开站、不做申请动作。

## 5. 交接点与确认点（完整清单）

交接点**就是下表全部各项**，没有其他类别，也不少于这些。到达前把能做的都做完（[连续推进](automation-continuity.md) 第 3–4 节），多家公司的同类交接合并成一条消息。

| # | 交接/确认点 | 何时 | 自动化模式能否跳过 | 记录字段 |
|---|---|---|---|---|
| H1 | 开始前必问各项 | Query | 否 | `batch.*` |
| H2 | 公司次序确认（可合并多家） | 公司申请动作前 | 否 | `company_order_*` |
| H3 | 名额不足时选岗 | 查到数量规则后 | 否 | `company.count_rule` + 选岗依据 |
| H4 | 资格待核/不符时是否尝试 | 资格复核后 | 否 | `role.eligibility.user_attempt_ref` |
| H5 | 跨轴冲突取舍 | 出现时 | 否 | `selection_ref` |
| H6 | 未开启的自动化子 Skill 步骤，或执行 Agent 声明不做的步骤 | 遇到时 | 开启后对应项可由 Agent 做 | 交接记录 |
| H7 | 本人物理动作：扫码、手机确认、生物识别、系统权限开启、证件号输入 | 遇到时 | 否 | 交接记录 |
| H8 | 缺失且只有用户能提供的事实 | 填表时 | 否 | 档案写入 |
| H9 | 志愿/意向部门/调剂等用户选择项 | 填表时 | 否（档案中的旧偏好只作建议默认值） | 目标确认 |
| H10 | 具体新法律协议、新增或扩大持续权限 | 遇到时 | 否 | terms-consent 记录 |
| H11 | 首次使用 computer use；用 Playwright 代替 Chrome 通道 | 需要时 | 否 | `batch.browser` |
| H12 | 三次确认分支（完整接手验证、微信截图交接、全部代勾） | 用户选择时 | 否 | `confirmation_refs` |
| H13 | 审核版本批准 | Review | 否 | `approval_ref` |
| H14 | 提交前目标确认 | 每次最终提交前 | 否 | `role.target_confirmation` |
| H15 | 结果不确定、站点与追踪表冲突 | 出现时 | 否（先查申请中心） | 第 7 节对账记录 |

## 6. 三种确认的区别（不要合并，也不要重复建清单）

| 确认 | 粒度 | 确认的是什么 | 依据 | 失效条件 |
|---|---|---|---|---|
| 公司次序确认 | 公司 | 该公司岗位相对本批默认次序是否变化 | 逐岗包 `pre_form_report_ref` | 新批次 |
| 审核版本批准 | 岗位 + 审核版本 | 这份表单内容可以提交 | `review_hash` | 第 8 节实质修改 |
| 提交前目标确认 | 每次提交点击 | 公司/BU/办公地/岗位/志愿槽位/数量规则这一确切目标 | 同一 `review_hash` | 目标任一项变化 |

三者复用同一份逐岗包和审核包，只是确认时刻和内容不同。前一种确认不能代替后一种。

## 7. 状态冲突时以谁为准

优先级：**站点账号申请中心/历史 > 官方回执（成功页、确认邮件、申请编号）> 私有批次记录 > 追踪表**。

- 续跑先读回这四方（`batch.resume_readback = {ref, read_at, conflicts: []}`），冲突逐条列出受影响岗位，不批量改状态。
- 站点显示已投而记录未投：记录改为 `submitted` 并补回执引用；**回执入账不受本批次序确认等其他前置项限制**。
- 记录为 `submit_clicked`/`uncertain`：先查申请中心再决定，查清前不重试。
- 恢复动作写 `role.recovery = {ref, result}`。
- 续跑复用同批授权（自动化、执行方式、Playwright 代替、computer use）时，在 `resume_readback.reused_authorizations` 列出所复用记录的引用；授权已撤销或范围变化的只重问变化项。

## 8. "实质修改"的定义

审核批准后，以下任一变化都是实质修改，生成新审核版本，旧批准失效：任何已填字段的取值、附件或材料版本、志愿/意向槽位、岗位或办公地、条款勾选状态、声明类回答。仅页面刷新、只读查看、截图、草稿再次保存（内容不变）不算。校验器把 `review_package` 的内容哈希与 `review_hash` 对比，不一致即视为审核后被修改。

限制：不得为了沿用旧批准而不记录修改；无法判断是否实质时按实质处理。

## 9. 计数补位规则

- `replace`：受阻（blocked）或核查后无合格岗位的公司**不计入**目标，剩余目标保持，从公司池按优先级补位。
- `keep_gap`：这类公司**计入**目标并作为"留空位"单独报告，不再补位。

## 10. 校验脚本的运行时点（必须运行，错误阻断）

| 时点 | 命令 | 有错误时 |
|---|---|---|
| Query 写入后 | `stage_gate.py <batch.json> --stage query` | 不进入 Prepare |
| 每家公司/岗位开始表单前 | `--stage prepare --role <role_key>` | 不开表单 |
| 进入 Review 前 | `--stage review --role <role_key>` | 不发审核包 |
| 每次最终提交点击前 | `--stage submit --role <role_key>` | 不点击 |
| 收尾前 | `--stage closeout` | 不宣布结束 |

脚本只做结构校验，不能证明网站真实保存或提交。每次运行记入批次记录 `gate_runs[]`。

**提交门禁由平台钩子强制执行。** `--stage submit` 通过后，脚本在 `投递证据/门禁通行证.json` 发放一张提交通行证：只对这一个岗位有效，10 分钟、最多 3 次点击（提交按钮加站点确认弹窗），该岗位在台账记为 `submitted`/`uncertain` 后立即作废。平台钩子 `hooks/application_guard.py` 在每次浏览器点击前检查：看起来是最终提交（按钮或描述含“提交”“投递”“我已知晓”“Submit”等）而没有有效通行证时直接拦截。安装见 [hooks/README](../hooks/README.md)。钩子只能识别带文字描述的点击；只给屏幕坐标的点击识别不了，仍须按上表先跑门禁。其他四个时点由 Agent 按上表执行。

## 10a. 严格证据模式与 `投递证据/`

投递根目录（用户建立的投递工作目录）下固定有一个 `投递证据/` 文件夹。台账里的**所有引用**都写成相对投递根目录的文件路径 `file:<相对路径>`：

- 证据字段（`*_ref`、`*_refs`）必须指向 `投递证据/` 里真实存在的文件；建议按 `投递证据/<batch_id>/<类别>/` 存放，类别如 `确认记录`、`截图`、`读回`、`回执`、`门禁`。
- **用户的确认也是证据**：批准、目标确认、次序确认、授权答复等，把用户原话和时间存成 `投递证据/<batch_id>/确认记录/*.json` 再引用，不写成一句文字。
- 普通 `ref` 字段（如 `sources[].ref`、`materials[].ref`）可以指向投递根目录里的其他文件，例如简历。
- 不允许绝对路径、指向投递根目录之外的路径、或纯文字描述。Windows 的反斜杠路径会被接受。

`validate_batch.py` 和 `stage_gate.py` 默认严格模式：从台账所在位置向上找到含 `投递证据/` 的目录作为投递根目录（也可 `--root` 指定），任何不合规的引用都报错并阻断。只有迁移旧台账时才用 `--lenient`。`投递证据/` 只放在用户私有工作区，不放进 Skill 目录，也不提交到公开仓库。

## 11. 批次能否结束（收尾检查）

`--stage closeout` 在以下任一情况返回不可结束，并列出原因与下一步：

- 还有 Agent 已获授权且能做的动作：岗位处于 `verified`/`preparing` 且未标 blocked；公司处于 `unvisited`/`checking` 且未标 blocked。
- 有 `submit_clicked`/`uncertain` 未对账。
- 数字目标仍有剩余，且未记录 `batch.stop_reached_ref`（用户确认停止、时间窗结束或公司池用尽的依据）。
- 无数字目标的分桶未记录 `batch.stop_reached_ref`。

收尾汇报时列出保留中的页面（公司、URL、阶段、是否受保护），写入 `batch.retained_pages_ref`；收尾不等于关闭页面，关闭仍按[页面保留规则](browser-application.md#page-retention)。

进度不足时的下一步：`replace` 规则下从公司池补位；公司池用尽则记录依据并请用户决定扩池或停止；时间窗将尽时先汇报差额再问。blocked 项只交给其解除方，不算 Agent 待办。

## 12. 邮件投递

本 Skill **不代发求职邮件**。只接受邮件投递的岗位：记 `blocked`，`unblock_owner: user`，`next_action` 写明"由用户自行发送或另行授权其他流程"；Agent 可只读查看用户邮箱已发送记录（已授权时）以避免重复，并把官方要求的邮件格式整理给用户。
