# 阶段契约：入口、问题时机、确认点、交接点与收尾

本文件是以下规则的**唯一出处**；其他文件只引用这里，不再复制条文。状态写在岗位追踪表（[追踪表契约](workbook-contract.md)），Query 答复与过程证据写在 `投递证据/<批次>/`（[目录与 Query.md](daily-batch.md)），由 `scripts/batch_check.py` 与 `scripts/stage_gate.py` 直接读取并做结构校验。公司方案 JSON 是 Excel 的同版本交接导出，不能独立改写；见[公司核对交接](company-review-handoff.md)。

## 1. 入口判定（谁来处理这个请求）

| 用户请求 | 判定 | 处理 |
|---|---|---|
| 只研究公司、收集岗位、整理岗位表，没有提出申请动作 | 研究 | 转工作区的研究/收集流程（如 campus-job-skills），本 Skill 不启动 |
| 对**已确认的岗位清单**或指定的现有岗位，要求准备表单、存草稿、审核或投递 | 投递 | 进入本 Skill |
| 同时要求"找岗位并投递" | 先研究再投递 | 发现与首轮 JD 核验由研究流程完成并写进追踪表；本 Skill 从表里的岗位开始，只做投递前复核，不重复首轮扫站 |
| 措辞不明 | 先问一句"这次是只收集岗位，还是要进入申请准备？" | 未答复前不开表单 |

判定写在 Query.md 的 `## 入口` 节（`类型: 投递` 与指向用户原话的 `依据:`）；类型不是投递时门禁不放行。

## 2. 启动读取与缺失处理

从工作区路由读取：私有档案、岗位追踪表、投递简历，以及本批 `投递证据/<批次>/`（续跑时）。简历等材料的路径和 SHA-256 写在 Query.md 的 `## 材料` 节，门禁会重新计算比对。

| 缺什么 | 处理 |
|---|---|
| 路由 | 请用户指出文件位置；不在 Skill 目录或公共目录里新建 |
| 个人档案 | 复制 [空白模板](../skills/personal-info-vault/assets/profile-template.md) 到工作区私有目录，登记后使用 |
| 本批 `投递证据/<批次>/` | 新批次：按 Query 新建；续跑：说明找不到并请用户确认是新批次还是指出旧批次，不凭记忆续跑 |
| 追踪表 | 请用户提供；没有追踪表就没有状态记录，不开始投递 |
| 投递简历 | 必问；没有确认的简历不开任何表单 |

## 3. Query：开始前必问 vs 到步骤前再问

**开始前必问**（一次问完，写进 Query.md 各节；任一项未定时，不开站、不登录、不开表单，只做离线整理）：

1. 硬范围：地区、届别、用工、岗位职责、城市。
2. 三条偏好轴与实习政策（见 [偏好契约](preference-contract.md)）。
3. 本批默认岗位类别次序。
4. 公司清单与分桶、计数口径（已查公司 / 有合格岗位的公司）、补位规则（补位 / 留空，见第 9 节）、数字目标或停止条件。
5. 投递材料（文件与 SHA-256）与选岗 / 准备授权范围（第 4 节）。
6. 执行方式：一个 AI 还是多个 AI。
7. 自动化子 Skill 开启方式与条款处理方式（[自动化授权](automation-authorization.md)）。
8. 能力预检结果与执行 Agent 声明不做的步骤（[连续推进](automation-continuity.md)）。

**到步骤前再问**（届时按公司汇总成一条消息，不在 Query 预先追问）：

- 每家公司相对默认次序有无变化（开始该公司申请动作前）。
- 简历和档案都没有的个人事实（填表时按公司汇总）。
- 志愿/意向部门/调剂/城市等用户选择项（填表时按公司汇总，Agent 只给建议）。
- 名额不足时选哪几个岗位（查到数量规则后）。
- 资格待核或不符时是否仍以真实材料尝试（资格复核后）。
- 跨轴冲突的取舍。
- 具体新法律协议的接受、新增持续权限（遇到时）。
- computer use 首次使用；第二通道缺 Chrome 插件且 Playwright 依赖不全时，请用户调整环境（需要时）。
- 审核版本批准与提交前目标确认（Review / Submit）。

## 4. 授权覆盖范围与必停情形

Query.md `## 授权` 节写明 `选岗授权: 是` 与 `准备授权: 是` 后，Agent **无需逐岗先问**即可：在已通过 HTML 完整确认的公司方案内准备已选岗位、登录（按已开启的子 Skill）、填写普通字段、上传已确认材料、保存草稿。`选岗授权: 否` 时每个岗位需要用户点名（岗位目录 `用户选岗.md`）。

即使已授权，以下情形**必须停下等用户**，且不受"全自动"影响：第 5 节交接点表中标为"否"的各项。"每家公司开始前确认次序"不要求逐家打断：可把多家公司的逐岗包合并成一条消息一次确认，未确认的公司只读开站、不做申请动作。

## 5. 交接点与确认点（完整清单）

交接点**就是下表全部各项**，没有其他类别，也不少于这些。到达前把能做的都做完（[连续推进](automation-continuity.md) 第 3–4 节），多家公司的同类交接合并成一条消息。每次用户答复都存成 `确认记录/` 里的文件。

| # | 交接/确认点 | 何时 | 自动化模式能否跳过 | 记录位置 |
|---|---|---|---|---|
| H1 | 开始前必问各项 | Query | 否 | `批次/Query.md` 各节 |
| H2 | 公司完整HTML方案及次序确认（可合并多家，复用搜索确认） | 公司申请动作前 | 否 | `公司/<公司>/次序确认.md` |
| H3 | 名额不足时选岗 | 查到数量规则后 | 否 | `公司/<公司>/选岗确认.md` |
| H4 | 资格待核/不符时是否尝试 | 资格复核后 | 否 | 岗位目录 `尝试指令.md` |
| H5 | 跨轴冲突取舍 | 出现时 | 否 | `确认记录/` |
| H6 | 未开启的自动化子 Skill 步骤，或执行 Agent 声明不做的步骤 | 遇到时 | 开启后对应项可由 Agent 做 | 交接消息 |
| H7 | 本人物理动作：扫码、手机确认、生物识别、系统权限开启、证件号输入 | 遇到时 | 否 | 交接消息 |
| H8 | 缺失且只有用户能提供的事实 | 填表时 | 否 | 私有档案 |
| H9 | 志愿/意向部门/调剂等用户选择项 | 填表时 | 否（档案中的旧偏好只作建议默认值） | `目标确认.md` |
| H10 | 具体新法律协议、新增或扩大持续权限 | 遇到时 | 否 | `确认记录/` |
| H11 | 首次使用 computer use；Chrome 插件缺失且 Playwright 依赖不全，请用户调整环境（Playwright 备用本身不需确认） | 需要时 | 否 | Query.md `## 能力预检` |
| H12 | 三次确认分支（完整接手验证、微信截图交接、全部代勾） | 用户选择时 | 否 | `确认记录/<分支>-1/2/3.md` |
| H13 | 审核版本批准 | Review | 否 | 岗位目录 `批准.md` |
| H14 | 提交前目标确认 | 每次最终提交前 | 否 | 岗位目录 `目标确认.md` |
| H15 | 结果不确定、站点与追踪表冲突 | 出现时 | 否（先查申请中心） | 第 7 节 |

## 6. 三种确认的区别（不要合并，也不要重复建清单）

| 确认 | 粒度 | 确认的是什么 | 依据 | 失效条件 |
|---|---|---|---|---|
| 公司方案确认 | 公司及版本 | 计划、全部目录、三档候选、推荐与最终选择、规则、内推及次序 | Excel导出的HTML及用户原话 | 方案实质变化或新批次 |
| 审核版本批准 | 岗位 + 审核版本 | 这份表单内容可以提交 | `审核包.md` 的 SHA-256 | 第 8 节实质修改 |
| 提交前目标确认 | 每次提交点击 | 公司/BU/办公地/岗位/意向/数量规则这一确切目标 | 同一审核包哈希 | 目标任一项变化 |

三者复用同一份逐岗包和审核包，只是确认时刻和内容不同。前一种确认不能代替后一种。

## 7. 状态冲突时以谁为准

优先级：**站点账号申请中心/历史 > 官方回执（成功页、确认邮件、申请编号）> `投递证据/` 记录 > 追踪表**。

- 续跑先读回这几方，写 `批次/续跑读回.md`；冲突逐条列出受影响岗位，不批量改状态。
- 站点显示已投而表格未投：把回执存进岗位目录并当场把 `投递状态` 改为 `已提交`；**回执入账不受本批次序确认等其他前置项限制**。
- 点击后无回执、结果不确定：写 `结果不确定.md`，先查申请中心再决定，查清前不重试。
- 续跑复用同批授权时，在 `续跑读回.md` 写明复用了 Query.md 的哪些节；授权已撤销或范围变化的只重问变化项。

### 7a. 中断后续跑（按中断位置）

| 中断在 | 现在怎么接 | 保护 |
|---|---|---|
| Query 中 | `--stage query` 列出缺的节，只补问这些 | Query.md 每节带依据 |
| 填表中 | 看 `batch_check.py` 报告的 `填写进度`，按岗位目录的 `填写方案.json` 接着填；缓存里已读回的字段先在页面复核，页面已丢（重载未保存）的退回待填重填 | 门禁只核对独立填写/草稿读回证据；缓存丢失可重建，不影响门禁 |
| 等审核/批准 | 用户回来后批准；表单若被改过，审核包哈希变化，旧批准失效 | §8 实质修改 |
| **点了提交、还没记下结果** | 钩子放行首次提交点击前已在岗位目录写 `提交已点击.md`（带通行证 ID）。有它而没有回执、`结果不确定.md` 或有效的 `提交核查.md` 时，**所有门禁拦截、不再发提交通行证**——包括新批次碰到同一岗位链接、以及新批次的 Query。先查申请中心：有记录就存回执并入账 `已提交`；查不清写 `结果不确定.md`（不再重投）；**确认没提交上**才写 `提交核查.md`（`标记哈希:` 当前标记的 SHA-256、`结论: 未提交`、`核验时间:` 晚于点击且 24 小时内、`来源:` 申请中心网址、`证据:` 投递证据/ 下的截图），之后可以重新走提交门禁，旧标记归档到 `提交尝试/` | 防止同一岗位重复投递 |
| 隔了很久（几天） | 提交前重新复核：`提交前复核.md` 的 `复核时间:` 超过 24 小时，或已核实的 `数量规则.md` 核验日期超过 7 天，提交门禁拦截；重新确认岗位仍在线、名额与表单未变后再提交 | 提交门禁的时效检查 |

## 8. "实质修改"的定义

审核批准后，以下任一变化都是实质修改，生成新审核版本，旧批准失效：任何已填字段的取值、附件或材料版本、志愿/意向槽位、岗位或办公地、条款勾选状态、声明类回答。仅页面刷新、只读查看、截图、草稿再次保存（内容不变）不算。审核版本就是 `审核包.md` 的 SHA-256：`批准.md` 和 `目标确认.md` 里写的哈希与当前文件不一致时，门禁视为审核后被修改。

限制：不得为了沿用旧批准而不更新审核包；无法判断是否实质时按实质处理。

## 9. 计数补位规则

- **补位**（replace）：标为 `无当年校招计划` / `无用户要求岗位` / `无法访问校招页面` 或受阻的公司**不计入**目标，剩余目标保持，从公司池按优先级补位。
- **留空**（keep_gap）：这类公司**计入**目标并作为"留空"单独报告，不再补位。表格里照常写对应的 `盘点状态`，`备注` 写“<日期> <批次>：留空，原因…”。

## 10. 校验脚本的运行时点（必须运行，错误阻断）

命令都带 `--workbook <岗位追踪表.xlsx> --batch <批次>`：

| 时点 | 命令 | 有错误时 |
|---|---|---|
| Query 写入后 | `stage_gate.py … --stage query` | 不进入 Prepare |
| 每个岗位开始表单前 | `--stage prepare --url <岗位链接>` | 不开表单 |
| 进入 Review 前 | `--stage review --url <岗位链接>`（要求独立 `填写读回.md`、草稿读回或无草稿说明及审核包；不读取 JSON 缓存） | 不发审核包 |
| 每次最终提交点击前 | `--stage submit --url <岗位链接>` | 不点击 |
| 收尾前 | `--stage closeout` | 不宣布结束 |

除 query 外，每个阶段都先跑整批一致性：扫过的公司必须有 `盘点状态`，回执必须入账为 `已提交`，反之亦然。所以表格没更新时，任何后续动作都会被拦下。脚本只做结构校验，不能证明网站真实保存或提交。`batch_check.py --where --company <公司> --url <链接>` 打印证据应存放的目录。

**提交门禁由平台钩子强制执行。** `--stage submit` 通过后，脚本在 `投递证据/门禁通行证.md` 发放一张提交通行证：只对这一个岗位有效，10 分钟、最多 3 次点击：**只放行一次首次提交**，其余只能是站点的确认弹窗（同一个批量调用里出现两次提交按钮会被拦下；多个点击同时到达时加锁串行），该岗位目录里出现 `回执.*` 或 `结果不确定.md` 后立即作废。每次放行的点击都会在岗位目录留下 `提交已点击.md`（见 §7a）。平台钩子 `hooks/application_guard.py` 在每次浏览器点击前检查：看起来是最终提交（按钮或描述含“提交”“投递”“我已知晓”“Submit”等）而没有有效通行证时直接拦截。安装见 [hooks/README](../hooks/README.md)。钩子只能识别带文字描述的点击；只给屏幕坐标的点击识别不了，仍须按上表先跑门禁。其他四个时点由 Agent 按上表执行。

## 10a. 严格证据模式与 `投递证据/`

投递根目录（用户建立的投递工作目录，追踪表就在这里）下固定有一个 `投递证据/` 文件夹，目录结构见 [daily-batch](daily-batch.md#目录)。

- 证据就是文件：门禁按约定的文件名检查是否存在，`依据:` 行必须是相对投递根目录、位于 `投递证据/` 下、真实存在的文件路径。
- **用户的确认也是证据**：批准、目标确认、次序确认、授权答复等，把用户原话和时间存成 `投递证据/<批次>/确认记录/*.md`，再在对应文件里用 `依据:` 指过去，不写成一句文字。
- 不接受绝对路径、指向投递根目录之外的路径或纯文字描述；Windows 的反斜杠路径会被接受。
- `投递证据/` 只放在用户私有工作区，不放进 Skill 目录，也不提交到公开仓库。

## 11. 批次能否结束（收尾检查）

`--stage closeout` 在以下任一情况返回不可结束，并列出原因：

- 公司清单里还有公司的 `盘点状态` 是 `尚未推进` 或空白，且没有 `受阻.md`。
- 岗位目录已开始，但既没有回执也没有 `受阻.md`（等待用户批准也要写 `受阻.md`，解除方: 用户）。
- 有 `结果不确定.md` 尚未在申请中心核查。
- 有 `提交已点击.md` 而没有回执也没有 `结果不确定.md`（点击后的结果还没核实）。
- 数字目标仍有剩余，或有不设数字目标的桶，而 `批次/收尾.md` 没有 `停止原因:` 和指向用户确认的 `依据:`。
- `收尾.md` 没有 `保留页面:`（列出仍打开的公司页面；收尾不等于关闭页面，关闭仍按[页面保留规则](browser-application.md#page-retention)）。

进度不足时的下一步：补位规则下从公司池补位；公司池用尽则记录依据并请用户决定扩池或停止；时间窗将尽时先汇报差额再问。受阻项只交给其解除方，不算 Agent 待办。

## 12. 邮件投递

本 Skill **不代发求职邮件**。只接受邮件投递的岗位：在岗位目录写 `受阻.md`（解除方: 用户，下一步: 由用户自行发送或另行授权其他流程），表格 `备注` 写明；Agent 可只读查看用户邮箱已发送记录（已授权时）以避免重复，并把官方要求的邮件格式整理给用户。

## 13. 搜索交接门禁

按[公司核对交接](company-review-handoff.md)接收Excel、HTML确认及同版本JSON。每个Prepare/Review/Submit在现有门禁之前调用随包company_handoff.check；未确认、不同步、不在最终选择中、特殊计划未考虑、规则/内推缺项或地区行不一致均阻断。Query和回执补记不因缺少新交接而被禁止，旧提交保护继续生效。Excel任何刷新后运行 `company_handoff.py export --workbook <表> --batch <批次>`；实质方案变化先更新版本、重新HTML核对再confirm。JSON不承担独立状态决策。
