REA 跨投递规则复用：最终分析存档

结论：本轮汇总中，首次 REA 学习和验证增加成本；后续复用已验证规则后，整体 token 和耗时下降。不能理解为每个网站或每次投递必然更快。

模型：gpt-5.6-sol / high。五类 mock，每类三组各一次，共 15 个独立模型回合。
无 REA（同样流程优化）：1,134,813 token，362.50 秒，38 次模型请求。
首次 REA（分析、空白页重放验证、保存规则）：1,343,533 token，431.71 秒，43 次请求，5 次 REA。
后续复用：824,169 token，325.45 秒，30 次请求，5/5 实际复用，0 次 REA。
首次相对无 REA：token 增加约 18.4%，总耗时增加约 19.1%。
复用相对无 REA：token 减少 27.4%，总耗时减少 10.2%。

机制：保存当前页面结构对应的参数化操作规则；后续用当前申请资料和当前控件执行，减少模型重复读取与决策。每次仍执行读回、服务端草稿核对、当前审核批准和提交门禁，不继承旧输入或旧批准。

边界：
1. 每网站每组仅一次。主机负载及模型提供方缓存未隔离，不能断言长期稳定的提速幅度。
2. 搜索下拉、日期级联的 token 降幅约 49%；其他三类复用 token 略增。日期级联复用耗时 110.64 秒，高于无 REA 的 68.25 秒，已保留。
3. 真实 token 来自 CLI usage 并独立审计；总耗时覆盖 CLI 启动到完整退出及错误重试。15/15 回合审计通过。token 比例不等于金额比例。
4. 全链路真实模型实测仅覆盖现有 Playwright 备用适配器。IAB/Chrome 的共享规则编译已单独验证，完整真实模型链路尚未实测。
5. 未比较“仅 UI 学习并缓存”第四组，不能据此证明 REA 是获得可复用规则的唯一途径。
6. 按观测值算术外推，额外复用一轮五站可抵消首次增加的 token，两轮可抵消首次增加的时间；这不是额外实测或稳定回本保证。
7. 人工批准在 mock 中显式模拟；真实站点调研、登录、验证码及人工等待未计入。
8. 本次无 REA 基线已有相同流程优化，不与历史不同基线报告混算。
