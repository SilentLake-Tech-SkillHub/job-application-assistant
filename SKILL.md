# 岗位代投助手 / Job Application Assistant

This Skill starts from a **confirmed role list** handed over by the research workflow or named by the user; first-pass discovery and JD collection are inputs, not steps here (entry criteria are in [stage contract §1](references/stage-contract.md#1-入口判定谁来处理这个请求)). Read [stage-contract.md](references/stage-contract.md) at the start of every batch: it is the single source for Query timing, the complete handoff/confirmation list, state precedence, “substantive change”, gate commands and closeout. **State lives in the role tracker (Excel), nowhere else**: every scanned company gets its `校招计划.盘点状态` label (one of five) and every role row its `投递状态`, exactly as defined by campus-job-skills' workbook schema ([tracker contract](references/workbook-contract.md)); there is no JSON ledger. Discover the workspace's private profile, role tracker and this batch's `投递证据/<批次>/` folder from its project router. Keep names, contact details, résumé paths, company lists, quotas, personal eligibility and referral information in private project records, never in this Skill or a public copy. Query answers and process evidence are files under the application root's `投递证据/<批次>/` folder, user confirmations included ([layout](references/daily-batch.md), [stage contract §10a](references/stage-contract.md#10a-严格证据模式与-投递证据)). The final-submit gate is also enforced by a PreToolUse hook on Claude Code, Codex and Kimi Code ([hooks/README](hooks/README.md)); install it once per workspace. Record the résumé and other materials with their SHA-256 in `Query.md`; handle a missing router/profile/tracker/batch folder/résumé as [stage contract §2](references/stage-contract.md#2-启动读取与缺失处理) says. A previous batch is evidence, not current authorization.

## Browser default and retained company tabs

By default run **two browser lanes in parallel: the agent's in-app browser and the user's Chrome through a Chrome extension (e.g. Claude in Chrome)**, assigning each company (recruiting entity plus shared account) to exactly one lane. **Playwright is the standing backup for the second lane**: when the Chrome extension is missing (or disconnects and cannot be reconnected), tell the user and run that lane with Playwright (`scripts/playwright_fill.py`, persistent profile that keeps logins) without a per-batch consent question; if Playwright's dependencies are missing, tell the user what to install and let them fix the environment (the Agent installs nothing), continuing with the in-app browser meanwhile. computer use and system scripts are not browser lanes and need the user's confirmation before first use. The single source for lane assignment, missing-lane handling and these boundaries is [browser division of work](references/browser-application.md#浏览器分工内置浏览器与-chrome-默认并行); follow [browser preparation and submission](references/browser-application.md). Page retention and closing follow the single rule in [page retention](references/browser-application.md#page-retention): nothing is closed without a separate explicit instruction naming the company/pages, and protected pages are never closed.

## Deterministic form preparation

For form preparation, use the [programmatic semantic mapping and REA diagnostics](references/semantic-form-automation.md) after the existing batch/form gates. The deterministic tools map clear fields to private profile sources, preserve education-group identity, compile the existing fill-plan schema and return only an exception summary to the Agent. All three browser lanes retain their own real input APIs; complex widgets need verified click recipes, and REA passive diagnostics are optional when the assigned lane already exposes an authorized CDP endpoint. Verified structural caches never replace current-page readback, user decisions or submission approval.

## Application execution-mode Query

Before a new application-preparation batch starts form actions, ask `本轮申请准备和投递由一个 AI 执行，还是由多个 AI 平行执行？` with the remaining Query choices. Record this application's choice and user evidence, separately from any search execution mode. Reuse a confirmed choice for the same batch; if the user already requests multiple AI, resolve only missing coordination facts. An unanswered question does not enable parallel work or dependent form actions; independent offline work may continue.

Single AI follows this parent's normal workflow. Confirmed multiple AI loads [application-parallel-execution](skills/application-parallel-execution/SKILL.md) before allocation or dispatch. This allows agreed preparation delegation across independent companies, with exclusive shared-account ownership and a serial tracker writer. It never replaces exact-role/current-review submission approval or changes the login, form-control and receipt gates below.

Before allocation, proactively ask about explicit requirements for participants, grouping, priorities, time and task quantities; if absent, invite the user's ideas and offer a reasoned proposal. Confirm it before dispatch. A numeric business target is optional: a confirmed scope or time window with an explicit stopping rule can be used instead. Counts and buckets belong to this batch; actual tool capacity and official account limits are separate constraints. See the parallel subskill for the proposal method.

## Automation authorization Query

Five automation subskills are **off by default**: [login-phone-otp](skills/login-phone-otp/SKILL.md), [login-wechat](skills/login-wechat/SKILL.md), [captcha-solve](skills/captcha-solve/SKILL.md), [privacy-info-fill](skills/privacy-info-fill/SKILL.md) and [terms-consent](skills/terms-consent/SKILL.md). Before any login or form action in a batch, ask whether to enable none, some (semi-automatic) or all (fully automatic), record the user's explicit answer, and invoke only the approved ones. An explicit choice of “fully automatic / 全自动” enables all five without another enablement question; record it and disclose their unchanged boundaries. Reuse valid same-batch authorization across turns and executor handoffs; ask only for missing or materially changed facts. Silence, vague consent or approval of something else (including approval to submit a role) leaves them off. Read [automation-authorization.md](references/automation-authorization.md) for the Query wording, modes, per-subskill permanent limits and the private record format. SMS results and graphical CAPTCHA completion default to the user; full verification takeover needs three explicit confirmations. WeChat only supports user-operated login with a permitted private screenshot handoff after three confirmations, never Agent OAuth approval. Ask whether to review terms individually or tick covered ordinary items throughout this application workflow; batch ticking needs three confirmations and retains platform-required agreement disclosure, per-action access approval and user-only steps. These are user-defined extra confirmations, not platform standards or permission waivers. Neither mode changes the per-role submission approval.

## Automation continuity (Issue #10)

The goal is **full automation**: the user appears only at steps that truly require them. In the Query, run the capability preflight in [automation-continuity.md](references/automation-continuity.md) — browser tool, computer use, system scripting, Playwright — and state up front any step this executing Agent will not perform under its own platform rules, with the alternative arrangement. During work, when an authorized control is unreachable, recover within the company's assigned browser lane; moving a company to another lane is a handoff, Playwright backs up the Chrome lane, and starting computer use follows the confirmation rules in [browser division of work](references/browser-application.md#浏览器分工内置浏览器与-chrome-默认并行). This never permits switching channels to perform a user-only action, click WeChat OAuth approval or bypass a denied action. Handoff points are exactly the list in [stage contract §5](references/stage-contract.md#5-交接点与确认点完整清单). Advance to the last step before a handoff point, then hand off with a screenshot, the single action needed and what happens next; keep working on other companies meanwhile and batch handoffs and target confirmations per company.

Throughput (Issue #11): after the Query, open the current confirmed company set in bounded groups using [browser tab grouping](references/chrome-window-grouping.md) and the selected browser's actual capabilities. The Chrome lane uses at most 10 webpage tabs per Agent-owned window and a new window before page 11. Protected pages stay retained. The grouping count does not expand the approved company scope. Present and confirm each company’s role/order package before application actions, then advance confirmed companies to their login handoff, and send one consolidated login request; while the user logs in, progress logged-in companies, then fill and submit company by company. See section 5 of [automation-continuity.md](references/automation-continuity.md).

## Independent preference and evidence contract

Query reads [preference-contract](references/preference-contract.md) and the [blank private template](references/preference-template.md): confirm hard scope separately from employment-path, city and direction relations, retaining weak/tied/unknown meanings. Prepare reuses full JDs and includes officially evidenced conversion internships last in the same report when the private policy is conversion_last; this does not require absence of formal roles or sufficient formal coverage; no weighted cross-axis choice. Before form actions present every role’s full evidence and actual fill/save/submit states. Review and closeout repeat this per-role package alongside existing target and form-version approval. A preference update preserves submissions and explicit selections and revisits only user-selected gaps, without restarting first-pass research.

## 任职资格门禁

搜索筛选、取岗、准备、审核和续跑必须读取[岗位任职资格核对](references/eligibility-check.md)。按完整JD分别判断职责范围与个人资格，必需条件、优先条件及待解释条件分别记录；搜索交付资格结论与个人证据缺口，投递在进入表单前结合当前材料复核。缺证据标待核，不把“待投递”、标题或匹配分当作可投；明确冲突不默认推进，用户针对具体缺口以真实材料尝试的指令单独保留。用户已剔除、既有已投与明确选岗不重置，最终目标及表单版本仍审核。

## Modes and authority

1. **Query**: ask the “开始前必问” items of [stage contract §3](references/stage-contract.md#3-query开始前必问-vs-到步骤前再问) together, and defer the “到步骤前再问” items to the step that needs them. Ask for this batch’s default role-category order and record its confirmation (new batches never inherit the previous order); confirm the batch's hard region/cohort/employment/function/city scope separately from its employment-path, city and direction preference axes (raw wording, weak/tied/unknown relations and current version), company classification, batch-specific counting buckets, optional numeric targets or another explicit stopping rule, counting and replacement rules, time window, current materials, and whether selecting roles and preparing forms is authorized. Record unresolved decisions. Do not start dependent browsing or forms while material scope is unresolved. Read [daily-batch.md](references/daily-batch.md). Write the answers to `投递证据/<批次>/批次/Query.md`, each section pointing to the user's own words, then run `scripts/stage_gate.py --workbook <追踪表> --batch <批次> --stage query`; errors block Prepare.
2. **Prepare**: before starting each company’s application actions, present its per-role company/BU/location/title/direct-link package and ask whether its order changes from this batch’s default. Several companies’ packages may be combined into one message and confirmed together; a company without a decision stays read-only (no login-to-apply, form or upload actions). Wait for the company decision; use this same package (the role folder's `岗位包.md`, with `公司/<公司>/次序确认.md`) through Review and the existing final target/version gate, without a duplicate standalone checklist. The confirmed batch may authorize the Agent to select roles within scope, handle login, fill fields, upload approved materials and save drafts without asking for each role first; the stops that this authorization never covers are the “否” rows of [stage contract §5](references/stage-contract.md#5-交接点与确认点完整清单). As soon as a company is scanned, write its `盘点状态` in the tracker; write each in-scope role as a `待投递` row. Before each role's first form action run `stage_gate.py … --stage prepare --url <岗位链接>`. Record the official company entry, every relevant plan, title and full visible JD, official job-ID/canonical-direct-URL identity, BU or 未披露, cities, employment type, direction, JD decision evidence, duplicate check and logged-in account limits. Present and persist the per-role pre-form report before form actions; conversion_last puts evidenced conversion internships last in the same report even when formal roles exist or coverage remains incomplete; ambiguous conversion evidence stays pending. Cross-axis conflicts require user choice. Preserve the role tracker as the fact source. Read [workbook-contract.md](references/workbook-contract.md) before tracker work and [browser-application.md](references/browser-application.md) before interacting with a site. Route login to [application-login](skills/application-login/SKILL.md) and form content to [application-content-fill](skills/application-content-fill/SKILL.md). Fill fast and resumably through the role's `填写方案.json` fill cache ([batch filling and fill cache](references/browser-application.md#批量填写与填写缓存三条通道通用)): build it from the control inventory or a site template, batch-fill native fields through the lane's own form interface (Playwright lane: `scripts/playwright_fill.py`), click real options for custom widgets, read every field back, and export `填写读回.md` with `fill_plan.py export`. The cache never holds 盘点状态/投递状态, approvals or receipts — those stay in Excel and Markdown evidence ([who writes what](references/workbook-contract.md#填写缓存与-excel-的分工)); sensitive fields keep only a `档案:` source and passwords, codes and ID numbers stay with the user. Facts come from the user's private profile via [personal-info-vault](skills/personal-info-vault/SKILL.md): build it once from the résumé with `scripts/profile_vault.py init` (plain-text base profile + résumé hash, so lookups read Markdown instead of the PDF), and write every new answer the user gives with `profile_vault.py add` immediately; `fill_plan.py vault-sync` then releases the waiting fields (it refuses while the profile still lacks the value). The profile lives in the user's workspace, never inside a Skill folder, and is never published. Preparation does not authorize final submission.
3. **Review**: provide the exact role list with company/title/direct URL/BU or 未披露/cities/employment/direction/JD basis and screening reason, separate actual fill/save/submit evidence, and a versioned, readable package of each completed form, materials, consequential answers, current account limit, unresolved fields and screenshots. Save the package as the role folder's `审核包.md`; its SHA-256 is the review version, so any [substantive change](references/stage-contract.md#8-实质修改的定义) produces a new version and voids the earlier approval. Run `--stage review` first. Keep the forms available. Request approval for the named roles and review versions only.
4. **Submit**: after that approval, apply the **application-count rule gate** and **pre-submission target confirmation gate** below, recheck the role, plan, quota, materials and form version (`提交前复核.md` with its `复核时间:`, valid 24 hours; a verified count rule is re-verified after 7 days), run `--stage submit --url <岗位链接>`; submit one application at a time. Confirm a success page and, where available, the application history or receipt. An ambiguous result triggers status investigation before any retry. Save the receipt in the role folder and set that row's `投递状态` to `已提交` in the same turn, then verify the saved workbook with `scripts/tracker_readback.py --record` (every later gate blocks while a receipt is unbooked).
5. **Resume/status**: reload the tracker, this batch's `投递证据/` folder and website status and reconcile them by the precedence in [stage contract §7](references/stage-contract.md#7-状态冲突时以谁为准) (site history > official receipt > evidence files > tracker); write `批次/续跑读回.md`. Reconcile uncertain or already submitted roles before acting — a role folder holding `提交已点击.md` without a receipt or `结果不确定.md` blocks every gate until the application center is checked ([stage contract §7a](references/stage-contract.md#7a-中断后续跑按中断位置)); resume form filling from `填写方案.json`, re-checking cached read-backs on the page first; a receipt may be recorded even while other prerequisites of this batch are pending. Continue independent companies when one role is blocked; never infer a successful submission from a button click, modal, redirect or draft.

The two hard gates below apply inside steps 2–4.

## Application-count rule gate (hard gate, Issue #12)

Before selecting roles for a company or asking the user to confirm them, establish that company's **application-count rules** for the logged-in account: how many roles may be applied to in total, whether several applications may run at the same time, whether there is a preference order, and whether a role can later be changed or withdrawn. Sources, in order: official application notice/FAQ, the apply page or its modal, the account's application history, then previously verified private tracker rules. Record the rule with source and date as `公司/<公司>/数量规则.md` (and the tracker's `校招冷静期` cell where verified).

Put the rule as the **first line** of the confirmation list. When the rule allows fewer applications than the roles the user wants, ask in that same confirmation which roles to use — never present more roles than the site can accept as if all could be submitted. If the rule cannot be found, write `未核实`, say what that risks, and confirm **only the first** target of that company; after the first submission reread the account state (`公司/<公司>/首次提交后读回.md`) before confirming or touching the company's next role. A selected role list is not evidence that the site accepts that many applications.

## Pre-submission target confirmation gate (hard gate, Issue #8)

Before every final submission click — in single-AI, semi-automatic and fully automatic modes alike — present the **complete submission target** to the user and wait for an explicit confirmation of that exact target:

- **投递数量规则**（可投岗位数、能否同时进行多个流程、志愿/变更规则及来源；见上节）
- **公司**（招聘主体与平台账号）
- **BU/业务集团/组织**（如适用：集团下实际接收简历的一级组织）
- **办公地**（该投递的落地城市/地点）
- **岗位**
- **意向部门 / 志愿槽位**（多意向按投递顺序逐项列出；第一、第二意向分别写明）

Rules: a general-purpose instruction such as 「帮我填写打勾提交」「后面的你帮我提交」 authorizes mechanics, **not** the target; it never satisfies this gate. Intention/preference slots (意向部门、志愿顺序、调剂选项) are **user-choice fields**: the Agent may propose options with reasoning but must not select them unilaterally. When a site exposes a target-confirmation panel (e.g. 意向投递弹窗), pause there, restate the filled slots, and require the user's confirmation before the final click. If the user cannot be reached, stop at pre-submit and record `待确认` — never click submit on an unconfirmed target. Termination is often irreversible (several sites permanently close a BU after withdrawal), which is why this gate cannot be waived by any automation mode. A preference stored in the private profile (e.g. 调剂) is only a suggested default for these slots, never a selection. Record the confirmed target as the role folder's `目标确认.md`, quoting the current 审核包 hash.

If the user asks only to research companies or collect jobs, use the workspace's research workflow instead of this Skill ([stage contract §1](references/stage-contract.md#1-入口判定谁来处理这个请求)). This Skill does not send application emails ([stage contract §12](references/stage-contract.md#12-邮件投递)). If they request a specific existing role, skip only Query questions already answered by current evidence; the review and submission boundaries still apply.

## Invariants

- Judge candidates from **title plus complete visible JD** and the confirmed role functions. A matching title alone is insufficient; an unfamiliar title can still qualify when the JD shows product ownership. Record inclusion or exclusion evidence for borderline roles. Do not convert a user's batch interpretation into a universal role definition.
- A company counts in one bucket only. Keep checked companies, eligible roles, prepared applications and verified submissions as separate numbers. A blocked or role-free company follows the confirmed replacement rule; it never counts as a prepared application. A prepared form needs fill readback plus a saved-and-reopened draft, or recorded evidence that the site has no draft (page kept open); a blocked company or action needs reason, unblock owner (never the Agent) and next action — see [daily-batch.md](references/daily-batch.md). Use [daily-batch.md](references/daily-batch.md) for the evidence layout and `scripts/batch_check.py` for counts and consistency.
- Respect official plan relationships, cohort rules, application windows, account quotas and existing submissions. Check the logged-in account immediately before preparing and again before submitting. Do not withdraw, delete or resubmit without a new specific instruction.
- Default application content comes from the user's designated application résumé. Follow explicit user instructions about content and material versions; otherwise, do not silently substitute an older résumé, historical application, auto-parsed text or project repository. Trace each field to its source and check auto-populated fields individually. Before writing, inventory the form controls and build a per-field action map. Text fields accept typing; selects, cascaders, radio/checkbox choices and date/year/month fields require their actual selection controls. Displayed input text alone is not a valid component selection. Use the content-filling subskill for longer accepted versions, missing facts, field limits and readback.
- Ordinary form controls may be operated within the user's confirmed batch authority. Login codes, WeChat confirmation, CAPTCHA handling, personal/contact fields and agreement checkboxes go through their automation subskills only when the user has enabled them for this batch; otherwise stop at that step and ask the user to do it. Ordinary verification clicks may proceed within the enabled workflow; graphical CAPTCHA completion defaults to the user and Agent takeover requires [captcha-solve](skills/captcha-solve/SKILL.md)'s three explicit confirmations, platform permission, retry limits and handoff rule; government ID numbers are always entered by the user. Check legal declarations, identity assertions and signatures against supported facts. Never retain credentials, codes, cookies or identity documents in the tracker, evidence files, replies or screenshots.
- Treat website drafts, final submission clicks, receipts and tracker updates as distinct stages. Persist the stage and evidence after each role so a new turn can resume without duplicate submission.

## Evidence and closeout

Load only the subskill needed for the current step. Login returns an account state and unresolved actions to Prepare; content filling returns a versioned field/source/readback package to Review. Use [preparation-scenarios.md](references/preparation-scenarios.md) for maintenance checks; a scenario review does not establish a live site's login or submission success.

Use the tracker specified by the workspace, without adding tracker columns or statuses on your own; a scanned company never stays `尚未推进`, and exceptions such as a kept gap or a block go in `备注`. Before each write, reread the live file and record a recoverable backup; change only the affected rows, then reopen the saved file and read back the company official entry, role URL, full JD and status. If another process changed the file, reconcile against the latest copy instead of overwriting it. Screenshots should show enough context to identify the site and step while masking personal details where possible.

Before closing a batch run `stage_gate.py … --stage closeout`: a batch cannot end while authorized Agent-doable work, unreconciled uncertain submissions or an unrecorded stop condition remain ([stage contract §11](references/stage-contract.md#11-批次能否结束收尾检查)). At closeout show every role’s company/title/direct URL/BU or 未披露/cities/employment/direction/JD basis and screening reason plus actual fill/save/submit states and evidence; login-only progress is not a prepared form. Report coverage and outcome separately: companies checked by batch-specific bucket, roles verified, forms prepared, submissions with receipts, uncertain results, blocked sites, remaining numeric targets where configured, and progress against nonnumeric stopping conditions. Report official account quotas separately. State exactly which evidence supports a completion claim. Read the relevant reference at the point of use; this entrypoint does not import other project Skills or private configuration into a public copy.
