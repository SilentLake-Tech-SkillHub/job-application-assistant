# 交接消费接口

公司/岗位定位由固定代码完成：公司编码读取唯一公司控件定义，岗位编码读取roleBindings中的引用；同公司岗位共享全部控件。岗位标题、链接和官方编号来自确认交接，页面身份来自原任务。采集sourceUrl仅用于证据，不作为其它岗位的执行路径。`template_rebind_role`仅补岗位引用，不生成新的控件资产。

## 职责边界

唯一输入是工作区 `岗位交接/公司/<公司编码>.json`：每家公司一份宽表，由搜索端 `company_store.py refresh/forward` 从主表投影生成；「批次」部分在用户正向评审确认（`forward-confirm` 登记原话与该公司的内容指纹）后才可读取。目录 `RECRUITING_HANDOFF_DIR` 指定，默认 `<工作区>/岗位交接`。旧的公司方案 JSON 文件或对象输入一律拒绝（`HANDOFF_BATCH_REQUIRED`）。本组件不做选岗、不转换 Excel；投递结果与链接观察回传见 application-outcome.md。

投递组件只用上游分配的公司编码 `C00001` 定位公司资产；岗位编码 `J000001` 用于确认当前岗位、顺序及最终回执。站点编码和 URL 保留为交接数据的值，不再作为公司或表单资产的主键，也不再分配 F 表单编码。主档 `companyForms`、唯一正式公司填写模板、页面采集、选项及真实核验结果均按公司编码保存；正式模板直接读 `<公司编码>.json`，不再读取公司/岗位到模板的第二层绑定表。

公司模板保存控件结构，当前岗位标题和身份从已确认岗位绑定到执行计划，真实页面仍独立核验。原交接数据存在多条站点记录时保留原值，以当前岗位的来源站点或已核对页面取得配置；不替上游合并、改写或选择岗位。登录配置从主数据 JSON 的 `login_configs` 按公司编码和来源站点编码读取，同时核对公司归属和站点域名。

旧数据须由一次性迁移完成公司键、引用与队列元数据转换，并验证个人事实、来源、岗位顺序及已有资产可用性不变；旧键对照不进入正常运行流程。

`role_queue_import` 不需要参数。它逐家核对「批次」状态为已交接/进行中、确认指纹与内容一致，按正向评审确认的公司顺序（「批次.公司顺序」，唯一来源）与志愿顺序冻结执行快照（志愿顺序只在志愿分组内排：分组内多个岗位须有用户给定的不重复正整数顺序，否则 `INVALID_CONFIRMED_ROLE_ORDER`）。队列任务只存公司编码、站点编码、岗位编码和顺序；岗位链接、投递链接、岗位名、材料在执行时现读该公司文件，并先核对该公司的确认指纹。内容指纹只覆盖本批选中岗位的执行字段及其站点，浏览器通道不计入指纹：状态推进、进度、其他公司变化都不影响；该公司内容被改则这一家的任务失效（`HANDOFF_CHANGED_AFTER_CONFIRMATION` / `ROLE_INPUT_CHANGED`），其他公司照常。

搜索端按作用域重新确认某一家（只改材料 `materials_only`、链接变更 `links_only`，并记下上一版指纹、选岗不变）后，用 `company_batch_refresh_materials`（批次）只换这一家的确认版本：只改材料时重置核验状态，链接变更时作废已打开的页面状态、从打开岗位重新开始。

## 状态

只准备主表状态为 `岗位待投递` 的岗位（批次只收这一种）；投递回传里已投递、已关闭的岗位跳过，不确定/受阻的岗位在用户处理前受保护。重复次序、重复岗位或岗位链接不在其站点域名上时阻断。

## 执行顺序

1. 以相同私有档案、队列目录、浏览器socket、申请资产目录启动两个MCP；`role_queue_import`先离线接收方案。
2. 从派发结果按本轮明确的岗位编码选择任务。定向续跑用 `role_advance({queueId,queueHash,taskId,roleId,authorization:{login:true,evidence}})` 连续推进本岗位到可填写状态；本次任务已有标签直接复用。
3. 公司／站点还没有登录配置时，组件先按固定规则写入首版最小配置（只有本人登录契约）并读回，再继续同一任务；本次写入的公司在结果的 `loginConfigsCreated` 里列出。旧调用返回 `COMPANY_LOGIN_NOT_CONFIGURED` 时走 `login_config_supplement`，再用 `role_advance` 继续原岗位。
4. 站点还没有入口配置时，组件在绑定页尝试首版入口采集，按实际点击与可见表单生成配置并读回；岗位编号只写 `$roleId`，不写死具体岗位。标题第一次读取失败先推进其他公司，再复查原任务；同一失败第二次按登记进入 `role_entry_fallback` 截图兜底。Agent核对当前画面：已经是申请表时保留当前页（需要时 `preserveCurrentPage=true`），用 `mode=report`、`report.alreadyForm=true` 原地进入下一步，有模板则填写、没有则建库，不重复点击；岗位名或编号缺失、不一致只记录，不阻断。需要点击时只用绑定页的候选按钮，回报按钮完整文字与同文字按钮从上往下第几个，组件核对实际落地后写首版入口配置；同文字多个记 `count`/`index`。真正登录页交本人登录；非表单、入口不存在或不唯一等仍返回具体错误与证据，按现有兜底处理，不停其他公司。
5. 登录态按真实页面及入口点击落地核对；未登录只挂起这一家公司，需要本人登录的公司汇总一条告知，其他公司继续。用户完成后不用回复，轮到原任务时组件自行复查并接续；批次状态中的 `loginRechecks` 保留原任务及轮询信息。岗位名或编号的观察不阻断共享简历表单。
6. `role_prepare` 核对同一任务→全部字段离线编译→填写→独立只读核验；新增问题强制登记私有JSON。`role_verify`可额外核验；`role_screenshot`保存原标签截图并遮盖密码/短信码。
7. 返回 `ready_for_user_review` 后交用户校验；该岗位准备完成才可开始顺序中的下一岗位。用户明确授权具体岗位的当前表单后，调用 `role_submit`，传当前模板 Hash、已通过核验的 `reviewRunId` 与用户原话。内核重新核验字段、敏感来源及附件，先记录尝试再点击一个真实按钮；只认官网回执，随后用返回的 outcome 调用 `application_closeout`。不确定结果禁止自动重试；普通填写工具与模板不能提交。

## 一个岗位任务 = 一张标签

任务记录里的 `pageId` 就是这个岗位的标签。打开、登录、进入申请、填写、恢复都只操作这张标签；网址只用来判断它现在走到哪一步（按登录配置 `entry` 的详情页/申请页规则），不拿网址去整个浏览器里另找页面。

- **有入口配方的站点**（`entry` 为 `declarative_transition` / `resume_modal` / `detail_to_form`）只走一条线：打开岗位链接 → 需要时在同一张标签登录、验证 → 登录后官网把标签送到首页等别处，就在同一张标签回到岗位链接 → `role_enter_application` 在这张标签点“投递”进入申请页。不直接打开存储的投递链接；投递链接只作记录。
- **没有入口配方的站点**：入口尚未采集的，进入申请页时由组件写入首版入口配置（见上文第 4 步），之后与有入口配方的站点相同；官网没有独立岗位页、且该站点已有覆盖申请页的表单模板时，才直接用 `投递链接`（`applyUrl`），不拼接链接。
- `role_open` 打开前先找本岗位已有的标签：重新导入延续下来的绑定（任务状态 `rebind_required`），或唯一一张本岗位的页面（岗位链接原址、按入口规则认出的本岗位详情页/申请页）。只接管没有被其他任务绑定的标签；同一岗位开着多张时返回 `ROLE_PAGES_DUPLICATED`（附标签编号，下一步 `role_close_extra_pages`），不替用户挑。找不到才新开一张。
- `role_enter_application` 只在绑定标签上进入：没有绑定 → `ROLE_PAGE_NOT_BOUND`（先 `role_open`）；绑定标签不在了 → `ROLE_EXISTING_PAGE_NOT_FOUND`（`role_resume`）；绑定标签不在本岗位页 → `ROLE_BOUND_PAGE_NOT_AT_ROLE`（`role_open`）。浏览器里别的“现成申请页”一律不用。点击会开新标签的站点，第一次点击前登记已有的同站标签，之后只认点击新开出来的那张（中断重试也一样）。
- 已进入过申请页、但标签现在不在申请页（例如登录过期被送到别处）：回到岗位链接重新点进入，原有填写、核验证明作废；`role_resume` 经用户允许恢复丢失标签时同样从岗位链接重新进入。
- 页面卡住（一直转圈）：`role_reload_page` 刷新这张标签，不另开；已开始填写的页面刷新会丢掉未保存的填写，须带用户同意的原话，刷新后填写与核验证明作废。
- 多余标签：`role_close_extra_pages` 关闭本站点不属于任何任务、也不是登记账号核对页的标签。岗位页、首页、验证页、空白页直接关；申请页样式的标签先截图返回，用户看过同意后带 `authorization.closeFormPages` 与用户原话再关。只关本站点标签，不关最后一张，不关浏览器。
- 本任务当前标签只识别“是不是登录页”（登录 URL、登录表单／验证码／密码框、“登录”按钮）；不读账号文本、退出按钮或会话选择器。是否已登录由入口点击后的落地页证明。
- 2026-11-16 补全（C42）：没登录时不跳登录页的站点——页头等处可点的“登录／请登录／登录注册”文字（不限按钮元素，只看元素自己的文字），以及带登录字样、有手机号／验证码／密码输入的对话框，都算登录入口。首版入口、入口兜底在点之前先看岗位页是否有登录入口，有就交登录流程；点之前核对按钮中心点没被挡住、按钮可用，否则不点并报 `*_BUTTON_COVERED`／`*_BUTTON_DISABLED`（详情带挡住它的元素类型、是否对话框）；点了没换页的错误详情带页面上可见对话框个数。
- 同一批次重复导入（`role_queue_import` / `company_batch_create`）：确认内容和执行方式都没变就返回原队列、原批次运行，不新建任务。内容变了才建新队列：旧队列与旧任务记录删除，旧批次运行关闭并释放它占着的公司；同一岗位的任务编号不变（按批次 + 岗位编码固定），已绑定的标签延续到新任务（`rebind_required`）。

登录后首页不等于返回原岗位。公司 `login_open` 只供内部调试。

正常运行及恢复只遵循工作区 `产品管理/求职配置.md`「浏览器」与当前宿主能力文件，接线方式见 [宿主集成](host-integration.md)。计时使用本轮真实开始时间，具体口径见下文「用户视角计时」。

## 一条脚本运行

在本包目录运行 `node scripts/run-confirmed-roles.mjs`。设置 `RECRUITING_HANDOFF_DIR`、`RECRUITING_PROFILE_JSON`、`RECRUITING_LOGIN_PRIVATE_DIR`、`RECRUITING_PRIVATE_DIR`（已有申请模板） 和 `RECRUITING_RUN_AUTHORIZATION_FILE`（已有本轮用户授权文件）；可选 `RECRUITING_ROLE_QUEUE_DIR`、`RECRUITING_BROWSER_SOCKET`、`RECRUITING_BROWSER_PROFILE_DIR`。

脚本通过正式 stdio MCP 协议读取已确认的公司文件、打开岗位、准备登录并按授权请求一次短信；到人工步骤暂停。用户在原页面完成后向该进程输入 `resume`，脚本只读确认并恢复原岗位，继续填写及独立核验，保存计时和截图，停在用户校验。`close`只关闭MCP客户端，浏览器/broker保留。人工未完成时不重复发码；错误明确返回，不自动重启浏览器。它不实现Excel处理或最终提交。

## 同账号多岗位并发

`role_queue_import({parallelRoles:true,authorizationRef:'明确并发授权引用'})` 启用同公司岗位并发；角色次序仅作枚举，跨公司边界仍按确认次序。登录保持账号级独占，一岗登录后其他岗位刷新并检查登录态复用；填写用 `roles_prepare_batch`，一次账号租约内按独立 pageId/URL 并发执行。所有计划先编译；任何任务失败后等待其他工作者结束再释放锁。不得用多个站点编码伪造同公司的并发。

链接只在三种情况下回报，都只记到 `投递回传.json`（按编码每条覆盖写），不改交接区：

- 投递链接为空、第一次核对进入申请页：`role_enter_application` 把真实申请页地址记为 `投递链接` 观察。已有投递链接时不记。
- 岗位链接或投递链接打不开（报错、到首页/列表页且无法进入申请）：调用 `role_report_link_failure({...任务, field:'岗位链接'|'投递链接', evidence})` 记“失效”观察。投递链接失效后，该任务改从岗位链接进入，到达申请页后按上一条报新地址；岗位链接失效的岗位等搜索端重新找到官网岗位页。
- 岗位链接打开后跳到编号不同的岗位页（如 `/zpdetail/<数字>` → `/job/detail?jobAdId=<另一编号>`），且页面岗位名与确认岗位名一致：本次按跳转后的编号继续，并把跳转后的岗位页（只保留入口规则声明的参数）记为 `岗位链接` 观察。岗位名缺失或不一致时仍在本任务内采用实际站点编号继续，只记录观察，不提出岗位链接更新。

编号不变的跳转不算变化，不回报。搜索端 `apply-observations` 预览“J000184 投递链接：空 → X”，用户确认后在原编码下覆盖主表、只重生成并按“链接变更”重新确认这一家；投递端只刷新这一家。有入口配方的站点一律从岗位页进入；没有入口配方的站点在已有覆盖申请页的表单模板时才直接打开投递链接，还没有模板时仍从岗位页进入，进入后先建库。`form_assets_status` 按站点编码列出登录配置、已封存模板和投递链接的缺口。

`role_enter_application` 只允许从核实的详情页进入申请表，核对岗位标题和真实返回 URL，落地页是登录页时返回登录交接；在表单页不会点击提交按钮。表单字段仍须各岗位完整建库。运行前已有 broker 时固定本轮实例，连接断开或窗口不明确时返回恢复问题，不能通过另开浏览器试错。

本人操作登录以当前任务标签是否为登录页、以及入口点击的落地页为准。旧 account.pageUrl、account.selector 字段保留在私有配置中，但判断登录不读取；账号文字不与主档比对。登录重定向由同一任务接续，完成登录后再校验岗位及填写页面。

用户视角计时使用 `RECRUITING_RUN_STARTED_AT` 传入本轮开始时间戳，直到最终结束时间戳，不扣模型思考、修复、人工等待。没有传入时只能声明进程耗时。表单与JSON一致仅证明执行一致性，正式文本仍先对照来源审核；来源备注与待核说明放元数据。

分身未运行或没连上时，Agent 发现后直接用 `browser_initialize_chrome`（或 `node scripts/chrome-clone.mjs start`）启动一次，断开或端口不在时用 `browser_restore_chrome` 恢复，不等用户、不当阻塞上报（需求文档 6.2）；MCP 启动与只读检查本身不启动浏览器，不开第二实例。已连接broker可被两MCP客户端复用，客户端重启不重启浏览器。

原标签身份失效时，role_resume 只可恢复到同一浏览器通道中、URL 与原任务完全一致且唯一的现有页面；恢复后重新检查登录态和岗位。不存在或重复时拒绝，不另开页面。

## 声明式通用入口

已有飞书与简历弹窗配方保持兼容。其他已核实的详情页到申请页跳转可用 `entry.kind=declarative_transition`，合同与实际证据要求见 [声明式入口](declarative-entry.md)。Chrome 和内置浏览器共同执行一个共享驱动；仅观察真实返回页，不构造申请 URL。未采到真实按钮或结果页证据时仍阻断，不以手工填表替代建库。

连续执行由 shared/confirmed-runner.mjs 编排，脚本只负责命令行输入输出；当前状态通过 Store 覆盖保存在私有 runs/confirmed-runner-current.json，业务结果沿用核心 TaskRecords。
