# 岗位代投助手 V2

Start from the workspace router, confirmed role scope, current materials and existing authorization. Reuse same-batch decisions; ask only genuinely missing facts. This package is the single maintained application runtime in the workspace. Project MCP and host Hook entrypoints resolve to this source tree. Private facts and new runtime state stay outside the package.

## Start and route

On explicit workflow startup, run `hooks/conversation_scope.py enable` in the host execution context with the installed private scope/policy paths and this batch's authorization reference. The script derives the current conversation from the host; never supply or copy a conversation ID. Reuse an active registration. Other conversations and forks remain independent. Read [conversation hooks](docs/conversation-hooks.md) for installation details. Check both modules with `runtime_info`, then use `workflow_next` / `form_route` for the existing-asset IF branch before any filling; the returned MCP evidence determines the next call.

1. Before opening websites, call `company_batch_create` with the upstream-confirmed company plan JSON and current preparation authorization, then `company_batch_take`. MCP extracts companies and splits Chrome/IAB work; the default capacity is ten companies per channel, twenty total. Multiple roles count as one company, and a shared verified login scope stays on one channel. Read [dual-browser batches](docs/company-batches.md) and [role entry](docs/role-entry.md). The upstream workflow owns selection, approval and Excel-to-JSON preparation. The entry consumes the confirmed JSON without converting Excel; native company-plan outcome persistence belongs to MCP internals; spreadsheet conversion and external tracker synchronization are outside this package. Do not invent selections, reorder company/role priorities or silently bypass missing input. Legacy explicit sequential/same-company runners remain supported; they are not the default new-batch coordinator.
2. Check the actual executor for each assigned browser channel. Chrome uses the existing managed broker; IAB uses the host's in-app browser executor and its independent login state. Never send an IAB assignment to Chrome as a silent fallback, or claim that the Chrome socket controls IAB. Follow each company's frozen role order; its first navigation is the confirmed role URL, and login stays bound to the original role and tab. Never attach to daily Chrome or invoke REA during normal use. Keep active browsers alive. Record user waits and blockers per company so independent tasks continue; dispatch alone is not execution evidence.
3. An authenticated result requires matching account and absent login form. Otherwise read the declaration returned by preparation; obtain the user's acceptance of that exact declaration before `login_accept_privacy`, then `login_request_sms`. Third-party login remains user-operated. Graphical verification is always user-operated. Return the handoff once; do not drag, solve, refresh or resend automatically. After the user completes it, call `login_resume_verification` to verify that the challenge disappeared and an SMS countdown is visible. A missing challenge alone does not prove that an SMS was sent. Use only the user's current code with `login_verify_otp`; do not retain it.
4. Login MCP invokes deterministic guards within every mutation. A failed guard stops dependent actions. A Hook does not schedule a model turn: this Skill reads the result and invokes the next permitted tool. Preserve independent work when one company waits for the user.
5. After user login, call `role_resume`: it must return `ready_to_fill`, matching account, original role URL and title on the original tab. A homepage or login success alone cannot release filling. Recheck existing application history/quota before preparation. Call `role_prepare` for the same queue task; it compiles, fills and independently verifies. Use `role_verify` for additional read-only verification, then provide the private report/screenshot for user review. Sequential mode releases the next role only after the earlier role is prepared for review. When the confirmed JSON explicitly enables `parallel_roles`, verify the shared login once, refresh/recheck each role account and use `roles_prepare_batch`; one account lease covers that batch while its distinct role pages run concurrently. Never launch a browser to resolve ambiguous window ownership.
6. Application MCP keeps control capture, conditional discovery, private profile registration, offline plan compilation, batch preparation and independent current-page verification. All newly discovered questions, optional fields and explicit omissions remain registered. For a company with a verified official schema recipe, `workflow_next` routes to `capture_form_definition` before DOM capture; read [official form definitions](docs/official-form-definitions.md). The definition is construction evidence and does not certify completed UI mapping or filling. This release still has the previous application engine; generic résumé import and full application agreement handling are pending. Only native text parsing is in scope; no OCR.
7. Before compiling, review employer-facing text against the designated source: source/audit notes, model caveats and missing-data explanations belong only in metadata. Structural validity and JSON/page equality do not prove content quality. The compiler rejects recognized editorial leakage; source-based semantic review remains required. Record user-perspective timing from the first timestamp to the final timestamp, including model work, repair and waiting without deductions.
8. Review the exact completed form and actual save state. No application submission is performed by the login MCP or this release's batch preparation. Keep target, review and final-submit authority separate.

Use the installed tool descriptions; return compact counts, exceptions and evidence references instead of full successful inventories. Company assets contain selectors/rules, never personal values. Ordinary private facts live in the user's JSON, authentication secrets remain ephemeral. Browser pages and unsaved work stay open. See [installation and test instructions](docs/login-mcp.md).

For the requested comparison of responsibilities still outside MCP, read [capability boundaries](docs/capability-boundaries.md). These boundaries distinguish implemented code from capabilities that still require work and live acceptance.

## Business status rules

Business application status remains `待投递` / `已提交`. Only an official receipt or application-history confirmation permits `已提交`; preparation, review and a submit click do not. Receipt verification is separate metadata. Uncertain results block retries. MCP validates fixed events and atomically persists outcomes in the confirmed native company-plan JSON. It does not synchronize Excel or other tracker files; the model cannot assign arbitrary business labels.
