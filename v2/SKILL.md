# 岗位代投助手 V2

Start from the workspace router, confirmed role scope, current materials and existing authorization. Reuse same-batch decisions; ask only genuinely missing facts. This package is the single maintained application runtime in the workspace. Project MCP and host Hook entrypoints resolve to this source tree. Private facts and new runtime state stay outside the package.

## Start and route

On explicit workflow startup, run `hooks/conversation_scope.py enable` in the host execution context with the installed private scope/policy paths and this batch's authorization reference. The script derives the current conversation from the host; never supply or copy a conversation ID. Reuse an active registration. Other conversations and forks remain independent. Read [conversation hooks](docs/conversation-hooks.md) for installation details. Browser channels come only from the once-detected capability file of this host (see [host integration](docs/host-integration.md)); `runtime_info` shows the recorded capability and whether each bridge is live. Never re-guess, launch or switch browsers yourself; a missing file returns `BROWSER_CAPABILITY_DETECTION_REQUIRED`. Read the workspace browser policy in `产品管理/求职配置.md`. Check both modules with `runtime_info`, then use `workflow_next` / `form_route` for the existing-asset IF branch before any filling; the returned MCP evidence determines the next call.

1. Before opening websites, call `company_batch_create` with the current preparation authorization; it reads only the user-confirmed per-company wide files `岗位交接/公司/<company code>.json` (identities are fixed codes: company C00001, site S0001, role J000001; links are values read at execution; see [role entry](docs/role-entry.md)), then `company_batch_take`. MCP extracts companies and splits Chrome/IAB work; the default capacity is ten companies per channel, twenty total. Multiple roles count as one company, and a shared verified login scope stays on one channel. Read [dual-browser batches](docs/company-batches.md) and [role entry](docs/role-entry.md). The upstream workflow owns selection, approval and Excel-to-JSON preparation. The entry consumes the confirmed JSON without converting Excel; native company-plan outcome persistence belongs to MCP internals; spreadsheet conversion and external tracker synchronization are outside this package. Do not invent selections, reorder company/role priorities or silently bypass missing input. Legacy explicit sequential/same-company runners remain supported; they are not the default new-batch coordinator.
2. Each assigned channel runs only on the executor recorded in the capability file: Chrome is the component's dedicated Chrome clone (fixed private profile, local DevTools port, shared by every host, started only by `scripts/chrome-clone.mjs` or `browser_initialize_chrome`), IAB is the host's built-in browser (only when it passed all three detection checks). Never send an IAB assignment to Chrome as a silent fallback, never use Playwright, browser-use or another browser tool outside this MCP, and never launch a Chrome yourself; the user's daily Chrome and its extensions are never used. Follow each company's frozen role order; its first navigation is the confirmed role URL, and login stays bound to the original role and tab. Never attach to daily Chrome or invoke REA during normal use. Keep active browsers alive. Record user waits and blockers per company so independent tasks continue; dispatch alone is not execution evidence.
3. An authenticated result requires matching account and absent login form. Otherwise `login_prepare` applies the single business authorization switch in code ([persistent business authorization](docs/generic-form-pipeline.md#持久业务授权)): switch 1 ticks the consent and returns `ready_to_request_sms`, then use `login_request_sms`; switch 0 or undecided returns `needs_user_login` for the user to finish on the same tab, then `role_resume`. Never ask the user to re-confirm a declaration, an agreement checkbox or the ID number. Third-party login remains user-operated. Graphical verification is always user-operated. Return the handoff once; do not drag, solve, refresh or resend automatically. After the user completes it, call `login_resume_verification` to verify that the challenge disappeared and an SMS countdown is visible. A missing challenge alone does not prove that an SMS was sent. Use only the user's current code with `login_verify_otp`; do not retain it.
4. Login MCP invokes deterministic guards within every mutation. A failed guard stops dependent actions. A Hook does not schedule a model turn: this Skill reads the result and invokes the next permitted tool. Preserve independent work when one company waits for the user. Follow `continuation.owner/state`: construction, mapping and recoverable technical gaps belong to the agent, not the user. Continue permitted next calls instead of ending a turn after every partial fill. Use `workflow_advance` for distinct companies already ready to prepare; do not blindly retry unchanged failures. The same agent-owned failure twice on one task or company returns `STOP_LOSS_REPEATED_FAILURE`: hand driver gaps to `workflow_handoff`, record ordinary gaps as blocked with `company_batch_record`, then move to other companies; a third identical call is refused until the code version changes.
5. After user login, call `role_resume`: it must return `ready_to_fill`, matching account, original role URL and title on the original tab. A homepage or login success alone cannot release filling. Recheck existing application history/quota before preparation. Call `role_prepare` for the same queue task; it compiles, fills and independently verifies. Use `role_verify` for additional read-only verification, then provide the private report/screenshot for user review. Sequential mode releases the next role only after the earlier role is prepared for review. When the confirmed JSON explicitly enables `parallel_roles`, verify the shared login once, refresh/recheck each role account and use `roles_prepare_batch`; one account lease covers that batch while its distinct role pages run concurrently. Never launch a browser to resolve ambiguous window ownership.
6. Application MCP keeps control capture, conditional discovery, private profile registration, offline plan compilation, batch preparation and independent current-page verification. All newly discovered questions, optional fields and explicit omissions remain registered. For a company with a verified official schema recipe, `workflow_next` routes to `capture_form_definition` before DOM capture; read [official form definitions](docs/official-form-definitions.md). The definition is construction evidence and does not certify completed UI mapping or filling. Resume import stages the approved local material and then recaptures portal-parsed fields. Attachment acceptance uses actual screenshots and the host image-capable model under the shared pipeline; CAPTCHA remains user-operated.
7. Before compiling, review employer-facing text against the designated source: source/audit notes, model caveats and missing-data explanations belong only in metadata. Structural validity and JSON/page equality do not prove content quality. The compiler rejects recognized editorial leakage; source-based semantic review remains required. Record user-perspective timing from the first timestamp to the final timestamp, including model work, repair and waiting without deductions.
8. Review the exact completed form and actual save state. Follow [persistent business authorization](docs/generic-form-pipeline.md#持久业务授权) and [attachment acceptance](docs/generic-form-pipeline.md#附件截图与模型验收): every attachment of a role is judged once in one vision-model call, the site's uploaded state is accepted when no vision model is reachable, and only a model mismatch blocks; never download attachments or compare file hashes, and never ask the user to confirm a photo. The login MCP and every preparation tool never submit. Final submission is only `role_submit`, after the user's explicit authorization for that exact role and current form; it binds the template hash and a verified review run, re-verifies the edit form once, enters a site's summary step directly without comparing it, counts only an official receipt, and is followed by `application_closeout` (see [application outcome](docs/application-outcome.md)). Keep target, review and final-submit authority separate.

One role task = one bound tab (`pageId` in the task record). Every step acts only on that tab; URLs only tell which step it is at. Never open, pick or switch pages yourself with a browser tool during a role task: `role_open` reuses this role's existing tab (carried binding or the unique unbound page of this role) and only opens a new one when none exists; on sites with an entry recipe it always goes role link → login in the same tab → `role_enter_application` clicks into the form in that tab, never straight to a stored application URL. Errors carry `details.nextTool` (`role_open`, `role_resume`, `role_close_extra_pages`, `login_open_identity`); call that tool. Use `role_reload_page` for a stuck page and `role_close_extra_pages` for duplicate tabs (form-like extras need the user's look and words first). Site entry configs change only through `scripts/site-entry.mjs` (preview → user's words → write); see [role entry](docs/role-entry.md) and [declarative entry](docs/declarative-entry.md).

Use the installed tool descriptions; return compact counts, exceptions and evidence references instead of full successful inventories. Company assets contain selectors/rules, never personal values. Ordinary private facts live in the user's JSON, authentication secrets remain ephemeral. Browser pages and unsaved work stay open. See [installation and test instructions](docs/login-mcp.md).

For the requested comparison of responsibilities still outside MCP, read [capability boundaries](docs/capability-boundaries.md). These boundaries distinguish implemented code from capabilities that still require work and live acceptance.

For internal first-time acquisition and structural repair, read [the generic form pipeline](docs/generic-form-pipeline.md). Use `capture_rea_structure → form_mapping_candidates → profile_map_questions → form_build_template` with the existing capture/options/probe/seal tools. REA supplements live page evidence; it does not supply executable selectors or grant readiness. Normal filling reuses sealed assets. Never use company-specific temporary generators or mark unsupported ordinary controls as `userOnly`. Report `summary.fields` separately from `summary.structure`; a matched section is not a filled field.

Host responsibilities are deployment choices, not agent-brand rules. A single host may execute the workflow; a deployment may instead assign execution and maintenance to different hosts. Read [host integration](docs/host-integration.md) for the configuration source and installation/migration procedure. Only a host configured as `executor` calls website-facing MCP tools. `RECRUITING_HOST_ROLE` defaults to `executor` for a new single-host installation; `maintainer` is an explicitly selected code-repair role. With `maintainer`, both MCPs answer read-only inspections only and refuse every stage tool with `HOST_ROLE_MAINTAINER_READ_ONLY` before any browser, profile or queue access; the launcher starts no browser and `conversation_scope.py enable` refuses registration. The maintenance host repairs shared code from MCP feedback and returns it for executor testing. Every enabled execution session rejects external browser tools, shell substitutes and direct runtime-asset edits, regardless of host name or conversation-ID format. Registration accepts only MCP-built draft references with a complete acquisition receipt; legacy evidence must be reacquired through MCP. Use `workflow_handoff` with actual preparation or verification run IDs for driver defects. The maintenance host follows [maintenance rules](docs/maintenance.md): aggregate failures with `scripts/failure-summary.mjs` and fix one class at a time, reproduce from stored evidence before live retest, assess the impact of any gate change on sealed assets before merging, and add frameworks only as registered adapters. Run `scripts/readiness.mjs` before merging a gate change, after the confirmed batch changes, and before an execution host starts.

## Business status rules

This component never changes the master table status. `application_closeout` validates fixed events against official evidence and overwrites the latest result for each role in `岗位交接/投递回传.json`. Only an official receipt or application-history confirmation counts as `submission_confirmed`; preparation, review and a submit click do not. `submission_confirmed` is also refused unless the role was filled by this MCP from the company's sealed form template in the current batch queue and passed independent verification (`role_prepare`/`role_verify`), so forms filled by hand cannot be recorded as submitted; build the company form first. This component never edits the handoff area's links. When a role's 投递链接 is empty, `role_enter_application` records the verified application page as an observation in `岗位交接/投递回传.json`; when a role link or application link does not open, `role_report_link_failure` records a failure observation with evidence (a redirect that still opens is not a change). The search side previews observations with `apply-observations` and writes the master table only after the user confirms; the next import reads the refreshed company file. `form_assets_status` (also returned by `company_batch_create`) lists, per site code, missing login config, sealed template and 投递链接. Uncertain or blocked results block retries until the user resolves them. The search side turns these results into “当前状态是X，更新状态是Y” through reverse review, and writes the master table only after the user confirms. The component does not read or write Excel; the model cannot assign arbitrary business labels.
